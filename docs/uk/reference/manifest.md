# Маніфест

Ця сторінка описує точну форму маніфесту: кожне поле, його тип, чи воно необов’язкове, і що з ним робить інсталятор. Вона призначена для тих, хто пише інсталятор іншою мовою, ніж TypeScript чи Rust.

Нижче трапляються два види тверджень. «Читач мусить» та «інсталятор мусить» означають вимоги формату. «Еталонна реалізація» описує те, що роблять крейти Rust `opys-core` (декодування) та `opys-runtime` (встановлення), і інша реалізація може їх повторювати або робити краще. Там, де ця сторінка каже, що значення читається певним чином, але без слова «мусить», так роблять ці крейти.

Зіп, що переносить маніфест, описано в [форматі бандла](/uk/reference/bundle-format). Змінні, які лаунчер мусить надавати, перелічено в [сторінці Змінні](/uk/launcher/vars).

## Принцип {#the-principle}

Маніфест повністю визначений. Кожен артефакт називає одне конкретне джерело, а також геш скрізь, де його можна мати. Ніщо в ньому не каже «latest», і ніщо не просить сервер підказати, який файл завантажувати. Інсталятор нічого не визначає: він не читає версію із сервера, не бере геш із заголовка чи з файла поруч і не виявляє джерело під час встановлення. Ці рішення приймає збірка, перш ніж маніфест буде записано. Див. [Основні поняття](/uk/guide/concepts).

Отже, інсталятор не приймає власних рішень. Еталонна реалізація виконує таке, по черзі:

1. Обчислює змінні (див. [Інтерполяція](#interpolation)).
2. Залишає артефакти, чиї `rules` виконано.
3. Пропускає кожен артефакт, чий файл уже є за шляхом `path` і проходить перевірку цілісності, а решту завантажує.
4. Перевіряє завантажене.
5. Розпаковує артефакти, що мають `extract`.
6. Прибирає файли, які називає `restrict`.

## Мінімальний маніфест {#a-minimal-manifest}

```json
{
  "vars": { "root": "/games/pack" },
  "artifacts": [
    {
      "path": "${root}/libraries/a/a-1.0.jar",
      "source": { "url": "https://example.com/a-1.0.jar" },
      "integrity": { "sha1": "da39a3ee5e6b4b0d3255bfef95601890afd80709" }
    }
  ],
  "launch": {
    "command": "/usr/bin/java",
    "workdir": "${root}",
    "args": ["-cp", "${root}/libraries/a/a-1.0.jar", "com.example.Main"]
  }
}
```

## Поля верхнього рівня {#top-level-fields}

| Поле        | Тип              | Обов’язковість                  | Відсутність означає | Примітки                                                                                                                                                                              |
| ----------- | ---------------- | ------------------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `format`    | integer          | обов’язковий у заголовку бандла | не застосовується   | Значення мусить дорівнювати `1`. Читач бандла відхиляє будь-яке інше значення, перш ніж читати решту. Окремий JSON маніфесту його не містить, і там еталонна реалізація його ігнорує. |
| `vars`      | object           | так                             | `{}`                | Відображення імені на [змінні](#vars).                                                                                                                                                |
| `artifacts` | array            | так                             | `[]`                | Масив [артефактів](#artifact). У бандлі це `artifacts.json`.                                                                                                                          |
| `launch`    | object           | так                             | запуску немає       | [Запуск](#launch). Для встановлення він не потрібен, а для запуску потрібен.                                                                                                          |
| `restrict`  | array of strings | так                             | прибирання немає    | Glob-шаблони. Порожній масив означає те саме, що й відсутність.                                                                                                                       |

Невідомі ключі верхнього рівня еталонна реалізація ігнорує. Не покладайтеся на це, вони не є частиною формату.

У бандлі `opys.json` містить `format`, `vars`, `launch` та `restrict`. `artifacts.json` містить масив артефактів. Контейнер описано на сторінці формату бандла.

## Артефакт {#artifact}

Артефакт це один файл: куди він потрапляє, звідки беруться байти і як файл перевіряється.

| Поле        | Тип                                              | Обов’язковість | Значення                                                                                                                                     |
| ----------- | ------------------------------------------------ | -------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `path`      | string                                           | ні             | Призначення. Інтерполюється перед використанням.                                                                                             |
| `source`    | [Source](#source)                                | ні             | Звідки беруться байти.                                                                                                                       |
| `size`      | integer, 0 or more                               | так            | Довжина в байтах. Еталонна реалізація використовує її для звітів про прогрес і для впорядкування завантажень. З файлом вона не порівнюється. |
| `rules`     | [Ruleset](#rules)                                | так            | Якщо відсутнє, артефакт застосовується завжди.                                                                                               |
| `integrity` | [Integrity](#integrity)                          | так            | Якщо відсутня, нічого не перевіряється.                                                                                                      |
| `extract`   | [правило розпакування](#extract) або масив таких | так            | Виконується після перевірки файла.                                                                                                           |
| `metadata`  | any JSON value                                   | так            | Еталонна реалізація встановлення його не читає. Вільне для потреб збірки.                                                                    |

Артефакт відхиляє будь-який ключ, якого немає в цій таблиці, так само як і джерело, див. [Суворе читання](#reading-strictly).

Збірка прибирає артефакти зі спільним шляхом і залишає останній. Еталонна реалізація встановлення їх не шукає. Вона завантажує два артефакти з одним шляхом в один файл `.partial` одночасно, і встановлення завершується помилкою вводу виводу.

Це нативна бібліотека для Linux, у тому вигляді, в якому плагін `minecraft` записує її для 1.21.1. Вона завантажується, перевіряється і розпаковується в каталог нативних бібліотек:

```json
{
  "path": "${library_directory}/org/lwjgl/lwjgl-freetype/3.3.3/lwjgl-freetype-3.3.3-natives-linux.jar",
  "source": {
    "url": "https://libraries.minecraft.net/org/lwjgl/lwjgl-freetype/3.3.3/lwjgl-freetype-3.3.3-natives-linux.jar"
  },
  "size": 1245129,
  "rules": "allow.os.linux",
  "integrity": { "sha1": "149070a5480900347071b7074779531f25a6e3dc" },
  "extract": {
    "into": "${natives_directory}",
    "clean": true,
    "excludes": ["META-INF/"]
  }
}
```

## Джерело {#source}

Джерело це об’єкт з рівно одним із двох ключів. Який ключ присутній, такий і вид. Позначки немає.

- `{ "url": "…" }`: завантажити файл через HTTP(S).
- `{ "blob": "<sha256>" }`: файл це елемент бандла `blobs/<sha256>`.

Наявність обох ключів або жодного з них є помилкою. `blob` мусить складатися з 64 малих шістнадцяткових символів. Будь-який інший ключ є помилкою.

```json
{ "source": { "url": "https://example.com/a-1.0.jar" } }
```

```json
{
  "path": "${game_directory}/config/pack.toml",
  "source": {
    "blob": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
  }
}
```

`url` інтерполюється (див. [Інтерполяція](#interpolation)). `blob` не інтерполюється.

Як еталонна реалізація завантажує URL: запит GET, приймається будь-який статус 2xx. Вона переходить за перенаправленнями і надсилає `User-Agent: opys/1.0`, бо деякі хости відхиляють запит без нього. Тіло потоком записується у `<path>.partial`, який перейменовується у `<path>` лише коли завантаження завершиться. Помилка будь-якого виду, включно зі статусом не 2xx, повторюється до трьох разів, з очікуванням 0.5 с, 2 с і потім 8 с між спробами. Блоб копіюється з бандла у `<path>.partial` і перейменовується так само, без повторів, бо очікування не допомагає локальному читанню.

### Блоб-артефакти не мають власної цілісності {#blob-artifacts-carry-no-integrity-of-their-own}

Блоб названо за sha256 його байтів, тож ця назва і є його цілісністю. Читач, що декодує такий артефакт, надає йому `{ "sha256": "<ідентифікатор блоба>" }`, а потім перевіряє його, як будь-який інший артефакт. Записувач пропускає `integrity` у блоб-артефакті.

Якщо блоб-артефакт таки має `integrity`, еталонна реалізація приймає його лише тоді, коли воно має запис `sha256`, рівний ідентифікатору блоба, порівнюваний так, як записано. `integrity`, що називає лише sha1, інший sha256, той самий sha256 великими літерами або взагалі не має записів (`[]`), відхиляється. Коли воно прийняте, інші записи відкидаються.

## Цілісність {#integrity}

`integrity` каже, як перевіряти файл за шляхом `path`. Це один об’єкт або масив об’єктів. Кожен об’єкт називає один геш під одним із таких ключів:

| Ключ     | Довжина в шістнадцятковій формі | Примітки |
| -------- | ------------------------------- | -------- |
| `sha1`   | 40                              |          |
| `sha256` | 64                              |          |
| `md5`    | 32                              |          |

Об’єкт без жодного з цих ключів є помилкою. Значення гешів порівнюються без урахування регістру. Читач не перевіряє їхню довжину, значення неправильної довжини ніколи не збігається, тож перевірка не проходить.

```json
{
  "integrity": {
    "sha256": "ce79869e1307ed8ee1e2baa86a412b1eb5b75d10a01006d788a6f968bcfaee94"
  }
}
```

```json
{
  "integrity": [
    { "sha1": "149070a5480900347071b7074779531f25a6e3dc" },
    { "md5": "d41d8cd98f00b204e9800998ecf8427e" }
  ]
}
```

Що з ним робить еталонна реалізація:

- **Перевірка.** Прочитайте файл за шляхом `path` і гешуйте його кожним названим алгоритмом. Файл проходить, якщо збігається хоча б один запис. Інсталятор, який вимагає збігу кожного запису, суворіший за еталонну реалізацію.
- **Немає записів.** Коли `integrity` відсутнє або є порожнім масивом, нічого не перевіряється і файл проходить.
- **Перед завантаженням.** Якщо файл уже є за шляхом `path`, він перевіряється і залишається, коли проходить. Файл, що не проходить, завантажується знову. Артефакт без `integrity` ніколи не перевіряється, тож наявний файл залишається без огляду.
- **Після завантаження.** Кожен викачаний файл перевіряється, і встановлення завершується помилкою зі списком тих, що не пройшли. Еталонна реалізація рантайму дозволяє своєму викликачу вимикати цей крок. Це прибирає лише перевірку щойно записаних файлів, перевірка файлів, що вже є на диску, виконується завжди.

::: warning
Пишіть один геш на об’єкт. Об’єкт із двома ключами гешів не є формою, яку визначає формат. Еталонна реалізація залишає один із них, з перевагою `sha256`, потім `sha1`, потім `md5`, і мовчки відкидає інші. Вона також ігнорує невідомий їй ключ, коли об’єкт має відомий геш поруч.
:::

## Розпакування {#extract}

`extract` каже, що робити з файлом, коли він уже на місці. Це один об’єкт правила, масив об’єктів правил або відсутність. Масив виконується по черзі.

Вид правила визначається тим, який ключ воно має:

| Наявний ключ | Вид          | Обов’язкові поля  |
| ------------ | ------------ | ----------------- |
| `file`       | вибірка      | `file`, `into`    |
| `matches`    | сканування   | `matches`, `into` |
| жоден        | вивантаження | `into`            |

Правило з обома полями `file` і `matches` читається як вибірка, а `matches` відкидається. Надавайте кожному правилу лише поля його виду: поле, що не належить до виду (`clean` у скануванні, `strip` у вивантаженні), відкидається мовчки.

### Вибірка {#pick}

Витягує один названий файл з архіву.

| Поле   | Значення                                                                        |
| ------ | ------------------------------------------------------------------------------- |
| `file` | Ім’я елемента в архіві, зіставляється точно. Воно мусить бути звичайним файлом. |
| `into` | Цільовий файл. Інтерполюється. Батьківські каталоги створюються.                |

Якщо архів не має такого файла, встановлення завершується помилкою.

### Сканування {#scan}

Витягує кожен елемент, що відповідає шаблону.

| Поле       | Обов’язковість | Значення                                                                                                         |
| ---------- | -------------- | ---------------------------------------------------------------------------------------------------------------- |
| `matches`  | ні             | Шаблон для імен елементів. Не інтерполюється.                                                                    |
| `into`     | ні             | Цільовий каталог. Інтерполюється. Створюється, якщо відсутній.                                                   |
| `includes` | так            | Додаткові шаблони. Елемент витягується, якщо він відповідає `matches` або будь-якому з них.                      |
| `excludes` | так            | Шаблони для елементів, які треба пропустити. Типово немає жодного.                                               |
| `strip`    | так            | Префікси, які треба прибрати з кожного імені елемента, випробовуються по черзі. Перший застосовний прибирається. |

Для `strip` простий рядок є буквальним префіксом. Рядок, що починається з `*`, прибирає все до першої появи решти включно. Тож `"*/"` відкидає верхній каталог архіву незалежно від його імені. Елемент, чиє ім’я після обрізання порожнє, пропускається. `matches`, `includes` та `excludes` перевіряються за іменем у тому вигляді, в якому воно збережене в архіві, до `strip`.

Так плагін `java` розпаковує кожен архів JDK. Верхній каталог архіву JDK може містити номер збірки, тож він обрізається за формою, а не за іменем:

```json
{ "matches": "*", "into": "${java_runtime_dir}/jdk-21", "strip": ["*/"] }
```

### Вивантаження {#dump}

Розпаковує весь архів або елементи, що проходять фільтр.

| Поле       | Обов’язковість | Значення                                                                                                                                              |
| ---------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `into`     | ні             | Цільовий каталог. Інтерполюється. Створюється, якщо відсутній.                                                                                        |
| `clean`    | так            | Коли `true`, каталог вилучається перед розпакуванням. Виконується один раз на каталог за встановлення. Типово `false`.                                |
| `includes` | так            | Коли присутнє, витягуються лише елементи, що відповідають одному з них.                                                                               |
| `excludes` | так            | Елементи, що відповідають одному з них, пропускаються. Коли відсутнє, еталонна реалізація використовує `["META-INF/"]`. Явне `[]` не виключає нічого. |

::: warning
`clean` вилучає каталог, перш ніж архів буде прочитано. Архів, що зберігається всередині власного каталогу `into`, видаляється ним, і розпакування завершується помилкою. Тримайте архів, що очищується, десь інде.
:::

### Зіставлення шаблонів {#pattern-matching}

Імена елементів зіставляються цим діалектом, який не є синтаксисом glob-шаблонів з `restrict`:

- `a/` або `a/*`: починається з `a/`.
- `a*`: починається з `a`.
- `*a`: закінчується на `a`.
- Усе інше: дорівнює шаблону.

Форми випробовуються в такому порядку, тож шаблон із `*` з обох боків читається за кінцевим `*`. Окремий `*` відповідає кожному елементу.

Вид архіву випливає зі шляху артефакта `path`. `.tar`, `.tar.gz` та `.tgz` це tar, усе інше читається як zip.

### Що записується {#what-gets-written}

Еталонна реалізація читає весь архів у пам’ять, а потім записує:

- Звичайні файли. Елементи каталогів пропускаються, а каталоги створюються в міру потреби у файлах, тож порожній каталог в архіві не створюється.
- З tar, символічні посилання, в Unix. У Windows вони пропускаються.
- Елемент tar, що має будь-який біт виконуваності, зберігає свій режим, в Unix. Елемент zip ніколи: його режим ігнорується, і файл отримує типовий.

Інсталятор не повинен дозволяти імені елемента вивести його за межі `into`. Ім’я, після `strip`, яке є абсолютним або піднімається через `..`, мусить відхилятися, і так само мусить відхилятися те, що записалося б крізь символічне посилання, створене попереднім елементом. Еталонна реалізація зупиняє встановлення на першому такому елементі, з помилкою розпакування, і нічого не записує туди, куди вказувало ім’я. Архів це чужий файл, і його імена елементів це єдине в ньому, що каже, куди писати.

### Порядок роботи {#order-of-work}

Розпакування виконується після того, як кожен артефакт викачано і перевірено. Для кожного застосовного артефакта, що має `extract`, його правила виконуються по черзі. Потім інсталятор записує порожній файл за шляхом `<path>.opys-extracted`. Розпакування виконується за кожного встановлення, пропуску для вже розпакованого архіву немає. Прибирання ніколи не вилучає файл `.opys-extracted`.

```json
{
  "path": "${library_directory}/com/example/a/1.0/a-1.0-natives.jar",
  "source": { "url": "https://example.com/a-1.0-natives.jar" },
  "integrity": { "sha1": "149070a5480900347071b7074779531f25a6e3dc" },
  "extract": [
    { "matches": "lib/", "into": "${natives_directory}", "strip": ["lib/"] },
    { "file": "LICENSE", "into": "${game_directory}/LICENSE.txt" }
  ]
}
```

## Правила {#rules}

**Набір правил** вирішує, чи застосовується щось на певній платформі. Це одне правило або масив правил. Там, де його немає, річ застосовується завжди.

Набори правил трапляються в артефактах (`rules`), в об’єктах [Val](#val-and-valset) і в гілках [змінних](#vars). Аргументи запуску та змінні середовища отримують свої умови через них.

**Правило** записується одним із двох способів, і обидва означають те саме. Читач мусить приймати обидва. Записувач може використовувати будь-який, еталонна реалізація використовує скорочений запис скрізь, де може.

### Скорочений запис {#shorthand}

Рядок із частин, розділених крапками:

```text
allow
disallow
allow.os.<name>
allow.os.<name>@<version pattern>
allow.arch.<arch>
allow.features.<feature>
```

`disallow` приймає ті самі форми, що й `allow`. Імена це `linux`, `windows` та `osx`. Архітектури це `x86`, `x86_64`, `arm`, `aarch64` та `any`. Шаблон версії це все після `@`, крапки включно. Ім’я ознаки це все після другої крапки, тож воно може містити крапки.

`any` приймається, але не є шаблоном на все. Правило порівнює архітектуру, як будь-яке інше значення, тож `allow.arch.any` виконується лише на платформі, чий `arch` є рядком `any`, який еталонна реалізація рантайму ніколи не повідомляє.

Усе інше є помилкою, включно з невідомою дією, невідомим іменем чи архітектурою, а також відсутнім іменем після `os`, `arch` або `features`.

### Розгорнутий запис {#expanded}

Об’єкт:

```json
{
  "action": "allow",
  "os": { "name": "osx", "version": "^1[0-3]\\.", "arch": "x86_64" }
}
```

```json
{ "action": "disallow", "features": { "is_demo_user": true } }
```

- `action` це `allow` або `disallow`. Обов’язкове.
- `os` необов’язкове. Усі його поля необов’язкові: `name` (`linux`, `windows`, `osx`), `version` (шаблон) і `arch` (одна з архітектур вище).
- `features` необов’язкове. Кожен ключ це ім’я ознаки, а кожне значення це `true` або `false`.

::: warning
Пишіть `os` або `features`, ніколи не обидва. Еталонна реалізація залишає `os` і відкидає `features`. Пишіть лише три імені `os`, п’ять архітектур і булеві значення ознак. Еталонна реалізація читає розгорнуте правило, чий `os` або `features` вона не може прочитати, наприклад невідоме ім’я ОС або значення ознаки, що не є булевим, так, ніби цього поля там немає. Це перетворює умовне правило на безумовне.
:::

### Обчислення {#evaluation}

Для заданої платформи (її `name`, `version` та `arch`) і набору увімкнених імен ознак:

1. Кожне правило має **умову**.
   - `os`: кожне присутнє поле мусить збігатися. `name` мусить дорівнювати імені платформи. `arch` мусить дорівнювати архітектурі платформи. `version` мусить відповідати версії платформи. Шаблон шукається, а не мусить покривати весь рядок, тож закріпіть його через `^` і `$`, якщо вам це потрібно. Поле, яке відсутнє, не перевіряється, і `os: {}` виконується завжди.
   - `features`: кожна названа ознака мусить бути увімкнена, коли її значення `true`, і не увімкнена, коли її значення `false`. Кожна з них мусить виконуватися.
   - Жодне: умова виконується завжди.
2. Правило **виконується**, коли його дія `allow` і його умова виконується, або його дія `disallow` і його умова не виконується.
3. Набір правил **виконується**, коли виконується кожне правило в ньому. Порожній набір правил виконується.

Тож `disallow` без умови не виконується ніколи, а `allow` без умови виконується завжди.

```json
["allow.os.linux", "disallow.features.demo"]
```

Він виконується в Linux, коли `demo` не увімкнено.

Платформа самої еталонної реалізація рантайму повідомляє `name` як `linux`, `windows` або `osx` для ОС, в якій вона працює (будь-яка ОС, крім Windows і macOS, це `linux`), `arch` як `aarch64` на збірці ARM64 і `x86_64` на будь-якій іншій, а `version` як порожній рядок. Тому шаблон версії там відповідає, лише якщо він відповідає порожньому рядку. Лаунчер, що використовує шаблони версій, мусить сам надавати справжню версію ОС. Увімкнені ознаки це список, який передає лаунчер, типово порожній.

Шаблони використовують синтаксис крейту `regex` мови Rust. Шаблон, що не є правильним виразом, не знаходиться, коли маніфест читається. Він завершує встановлення помилкою, коли правило обчислюється, а його `name` та `arch`, якщо вони в ньому є, збіглися.

## Val і Valset {#val-and-valset}

**Val** це один аргумент запуску або їхня група, з правилами, що його обмежують. Це рядок або об’єкт:

```json
"-Xmx2G"
```

```json
{ "rules": "allow.os.osx", "value": ["-XstartOnFirstThread"] }
```

- Окремий рядок це те одне значення, без правил.
- Об’єкт має `value`, обов’язкове: рядок або масив рядків. Він має `rules`, необов’язкові, які є [набором правил](#rules).

**Valset** це масив Val. Він розгортається по черзі: для кожного Val, чиї правила виконано, його значення додаються по черзі. Кожен підсумковий рядок є одним аргументом. `launch.args` це Valset.

## Змінні {#vars}

`vars` відображає ім’я на **ValDef**. ValDef це або рядок, що використовується як є на кожній платформі, або масив **гілок**. Гілка це об’єкт:

```json
{ "value": "${java_home}/bin/java.exe", "rules": ["allow.os.windows"] }
```

- `value` це рядок. Обов’язкове.
- `rules` це набір правил. Необов’язкові. Коли відсутні, гілка застосовується завжди.

Гілки обчислюються по черзі. Перемагає **остання** гілка, чиї правила виконано. Якщо не виконано жодної гілки, ім’я взагалі не задається, і посилання на нього залишається як записано. Простий рядок не фільтрується за платформою.

```json
{
  "java_bin": [
    { "value": "${java_home}/bin/java", "rules": "allow.os.linux" },
    { "value": "${java_home}/bin/java", "rules": "allow.os.osx" },
    { "value": "${java_home}\\bin\\java.exe", "rules": "allow.os.windows" }
  ],
  "launcher_name": "opys"
}
```

`launch.envs` це також відображення ValDef. Його значення інтерполюються так само.

## Інтерполяція {#interpolation}

Шаблон може містити `${name}`. Ім’я це один або більше символів, серед яких немає `}` і пробільних. `\${` це буквальний текст `${`, зі знятою похилою рискою. Підставлений текст повторно не переглядається.

Порядок розгортання:

1. **Вибір.** Для кожного імені у `vars` виберіть його значення: простий рядок або останню виконану гілку, з платформою і набором ознак у руках. Ім’я без виконаної гілки не задається.
2. **Накладання.** Власні значення лаунчера замінюють однойменні записи і додають інші. Сюди потрапляють змінні зі [сторінки Змінні](/uk/launcher/vars).
3. **Розгортання посилань.** Власні посилання `${…}` кожного значення замінюються розгортанням того значення, рекурсивно. Це охоплює кожне значення, включно зі значеннями лаунчера, і кожне ім’я, використане чи ні. Цикл є помилкою. Посилання на ім’я, якого ніщо не визначає, залишається як записано.
4. **Інтерполяція.** Посилання в кожному полі шаблону нижче замінюються.

Коли `root` задано як `/g`, а `lib` як `${root}/libraries`, шлях `${lib}/a.jar` стає `/g/libraries/a.jar`.

Ці поля інтерполюються:

- `path` артефакта.
- `url` джерела.
- `into` будь-якого правила розпакування.
- Кожен запис `restrict`.
- `command` і `workdir` запуску `launch`, кожен елемент `launch.args` і кожне значення `launch.envs`.

Ці не інтерполюються: `blob`, `file`, `matches`, `includes`, `excludes` і `strip` правила, `rules`, `metadata`.

## Запуск {#launch}

`launch` це об’єкт. Він каже, як стартувати гру, коли файли вже на місці.

| Поле      | Тип            | Обов’язковість | Значення                                                     |
| --------- | -------------- | -------------- | ------------------------------------------------------------ |
| `command` | string         | ні             | Програма для виконання. Інтерполюється.                      |
| `workdir` | string         | ні             | Робочий каталог. Інтерполюється. Лаунчер може його замінити. |
| `args`    | Valset         | так            | Аргументи, по черзі. Типово `[]`.                            |
| `envs`    | map of ValDefs | так            | Змінні середовища для додання. Типово `{}`.                  |

Кожен розгорнутий аргумент інтерполюється окремо і є одним аргументом. Змінна не може розгорнутися в кілька. Еталонна реалізація рантайму стартує процес із `command`, `args` і `workdir`, а `envs` додає до успадкованого середовища. `envs` не замінює це середовище.

## restrict і прибирання {#restrict-and-the-sweep}

`restrict` це список glob-шаблонів для файлів, яких там не повинно бути. Він читається після того, як кожен артефакт встановлено і розпаковано. Порожній або відсутній список означає відсутність прибирання.

Glob-шаблон спочатку інтерполюється, а потім зіставляється з цілим шляхом файла за такими правилами:

- `*` відповідає будь-якому прогону символів, крім `/`.
- `?` відповідає одному символу, крім `/`.
- `**` відповідає будь-якому прогону символів, включно з `/`.
- `**`, що заповнює цілий сегмент шляху, може також відповідати жодному каталогу: `a/**/b` відповідає `a/b`, а `**/b` відповідає `b`.
- `/**` у кінці відповідає самому каталогу і всьому під ним.
- `{a,b}` відповідає будь-якій з альтернатив. Альтернативи це буквальний текст, тож `*` в одній відповідає `*`, і вони не вкладаються. `{` без `}` після неї відповідає сама собі.
- Усе інше, включно з `[` і `]`, відповідає саме собі.

**База** кожного glob-шаблона це текст до перших `*`, `?`, `{` або `[`, обрізаний назад до останнього `/`, який до неї не входить. Прибирання працює під кожною базою, і воно дивиться лише на файли під базою, що існує. Glob-шаблон без бази, такий як `*.jar` або `**/x`, пропускається без помилки.

Під кожною базою прибирання обходить дерево. Звичайний файл вилучається, коли виконуються всі ці умови:

- його шлях відповідає одному з glob-шаблонів цієї бази;
- його шлях не є кінцевим шляхом артефакта, що застосовується на цій платформі;
- його ім’я не закінчується на `.opys-extracted`.

Каталоги обходяться, а символічні посилання не відстежуються і не вилучаються. Потому кожен порожній каталог під базою вилучається, від найглибшого, незалежно від того, чи відповів йому glob-шаблон. Сама база зберігається. У Windows шляхи порівнюються без урахування регістру, а `\` читається як `/`.

З наведених правил випливають два наслідки.

- Файл, що його записує розпакування, не є артефактом. Glob-шаблон, що покриває ціль витягування, вилучає витягнуте, бо прибирання виконується після нього.
- Еталонна реалізація порівнює шлях артефакта зі шляхом файла як рядки, а не як файли. `${root}/mods/a.jar` і `${game_directory}/mods/a.jar` це різні рядки, коли `game_directory` це `${root}/`, як визначає його плагін `minecraft`, тож glob-шаблон, записаний одним чином, прибирає артефакт, записаний іншим. Записуйте артефакт і glob-шаблон, що його покриває, тими самими змінними.

```json
{ "restrict": ["${game_directory}/mods/*.jar", "${game_directory}/config/**"] }
```

## Канонічний запис {#canonical-spelling}

Читач мусить приймати кожен запис із цієї сторінки. Формат не вимагає від записувача вибирати один, але записувач, що хоче побайтово збігатися з еталонною реалізацією, пише канонічний, який породжує записувач еталонної реалізації:

- Правило записується скороченим записом, коли воно має його форму: окремий `allow` або `disallow`, `os` з іменем і необов’язковою версією, `os` з архітектурою і без імені, або `features` з одним іменем. Усе інше, таке як `os` лише з версією, порожній `os` або кілька ознак, записується розгорнуто.
- Набір правил з одним правилом записується як те правило, окремо. З кількома це масив. Без жодного `rules` пропускається в артефакті і в гілці. Val без правил пише `"rules": []`.
- Val з одним значенням і без правил це окремий рядок. Будь-який інший Val це об’єкт: `value` завжди є масивом, а `rules` завжди записується, як `[]`, коли їх немає.
- Гілка без правил не має ключа `rules`.
- `integrity` з одним записом це об’єкт, а не масив. Блоб-артефакт не має `integrity`.
- `extract` з одним правилом це те правило, окремо. З кількома це масив.
- `vars` і `artifacts` завжди записуються, навіть порожні. `launch` записується цілком, з `args` і `envs`, навіть коли вони порожні. `restrict` записується лише коли має записи.

::: warning
Записувач еталонної реалізації вибирає скорочений запис за формою правила і не перевіряє, що він каже те саме. `os` з `name` записується як `os.<name>`, тож його `arch` втрачається. `os` з `arch` і без `name` записується як `arch.<arch>`, тож його `version` втрачається. `features` з одним записом записується як `features.<name>`, тож `false` стає `true`. Не покладайтеся на кругову подорож через нього для таких правил.
:::

## Суворе читання {#reading-strictly}

Еталонна реалізація відхиляє невідомі ключі в артефакті і в джерелі, а також відхиляє об’єкт цілісності, що не має жодного з `sha1`, `sha256` або `md5`. Це ті місця, де невідомий читачу ключ міг би змінити перевірку файла, і формат каже так навмисно.

Скрізь інде еталонна реалізація ігнорує ключі, яких вона не знає. Реалізація може теж їх відхиляти і повинна так робити там, де ключ міг би змінити те, що встановлюється.
