# Бандл

Ця сторінка описує бандл на рівні байтів: файл, який записує команда `opys build` і з якого лаунчер виконує інсталяцію. Вона призначена для всіх, хто пише читач або записувач іншою мовою, ніж TypeScript чи Rust. Що містять два елементи з JSON, це справа [маніфеста](/uk/reference/manifest); ця сторінка пояснює, як вони запаковані.

Бандл є zip-файлом. У ньому немає нічого особливого для opys: його відкриває `unzip`, як і будь-яка бібліотека для zip.

Нижче трапляються два види тверджень. «Читач мусить» і «записувач мусить» є вимогами формату: бандл або реалізація, які їх порушують, є неправильними. «Еталонний читач» і «еталонний записувач» описують поведінку реалізації на Rust, яку інша реалізація може повторити або покращити. Там, де сторінка цього сайту каже «еталонна реалізація», йдеться про те саме.

## Елементи {#entries}

Бандл містить елементи трьох видів:

| Елемент          | Стиснення              | Вміст                                              |
| ---------------- | ---------------------- | -------------------------------------------------- |
| `opys.json`      | stored (без стиснення) | Заголовок: `format`, `vars`, `launch`, `restrict`. |
| `artifacts.json` | deflate                | Список артефактів: масив JSON.                     |
| `blobs/<sha256>` | deflate                | Один елемент на кожен блоб, який називає маніфест. |

Стовпець стиснення показує, що робить еталонний записувач. Еталонний читач відкриває кожен елемент через каталог zip, тому він приймає будь-який метод для кожного елемента.

`<sha256>` є ідентифікатором блоба: 64 малі шістнадцяткові цифри, sha256 байтів, які містить елемент. Еталонний записувач не пише інших елементів, а еталонний читач ігнорує всі, які знаходить.

Заголовок і список розділено, бо їх читають з різних причин і вони мають різний розмір. Список має один рядок на кожен файл інсталяції і виростає до мегабайтів (близько 1,3 МБ для ванільного прикладу); його читає лише інсталятор. Заголовок є малим файлом (близько 24 КБ для ванільного прикладу), і саме про нього питає все інше, наприклад яка версія лежить у бандлі або які змінні він залишає відкритими. Тому еталонний записувач кладе заголовок першим і зберігає його без стиснення. Читач може зчитати його з початку файла без розбору каталогу zip, а інструмент може прочитати весь заголовок за один пошук.

Елемент `blobs/` записується лише для блоба, який називає певний артефакт. Той самий блоб, який називають два артефакти, записується один раз.

## Порядок елементів {#entry-order}

Еталонний записувач пише елементи в такому порядку:

1. `opys.json`
2. `artifacts.json`
3. `blobs/<id>` для кожного окремого ідентифікатора блоба, у порядку зростання ідентифікатора як рядка

Формат не фіксує порядок. Читач мусить знаходити елементи за іменем і не повинен залежати від їхнього порядку; еталонна реалізація без проблем читає бандл, у якому заголовок останній. Заголовок стоїть першим лише для того, щоб його можна було прочитати з початку файла, як показує розділ [Читання лише заголовка](#reading-the-head-alone).

## Заголовок {#the-head}

`opys.json` є об’єктом JSON. Його поля:

| Поле       | Коли записується               | Значення                                                 |
| ---------- | ------------------------------ | -------------------------------------------------------- |
| `format`   | завжди                         | Ціле число. Див. [Поле format](#the-format-field).       |
| `vars`     | завжди                         | Об’єкт з визначеннями змінних. Порожній має вигляд `{}`. |
| `launch`   | коли маніфест має блок запуску | Команда запуску.                                         |
| `restrict` | коли список непорожній         | Список рядків.                                           |

Записувач пропускає `launch`, коли його немає, і пропускає `restrict`, коли його немає або він порожній. Читач трактує відсутній `vars` як `{}`, а відсутні `launch` або `restrict` як відсутні.

Еталонний записувач пише заголовок з відступами, а список артефактів компактно. Читач мусить розбирати обидва як JSON і не повинен залежати від пробілів.

## Поле format {#the-format-field}

`format` є версією формату бандла. Ця версія має номер `1`. Еталонна реалізація читає й пише `1` і нічого іншого.

Читач мусить:

- читати `format` раніше, ніж будь-що інше в заголовку;
- відхиляти бандл, якщо `format` не є цілим числом `1`, зокрема коли його немає, коли це не ціле число або коли це рядок на зразок `"1"`. Еталонний читач також відхиляє `1.0`;
- відхиляти його, перш ніж тлумачити `vars`, `launch`, `restrict` або список артефактів. Пізніший формат може записувати їх так, що версія 1 їх не розбере.

Еталонний читач повідомляє про неправильне число як про невідомий формат, а про відсутній або неправильно типізований `format` як про помилку розбору. Обидва випадки відхиляють бандл.

Читач не відхиляє бандл через ім’я чи розширення файла. Див. [Ім’я файла](#the-file-name).

Еталонний читач ігнорує невідомі поля заголовка. Невідомий `format` він не ігнорує.

## Блоби {#blobs}

Блоб є файлом, який маніфест везе всередині бандла. Артефакт називає його через `"source": { "blob": "<id>" }` замість URL. Ідентифікатор є sha256 байтів файла, і це єдина назва, яку має блоб. Його розташування в бандлі: `blobs/<id>`.

Ідентифікатор є також перевіркою цілісності. Артефакт блоба не має власної `integrity`: ідентифікатор є очікуваним sha256 байтів. Читач, який встановлює артефакт, перевіряє прочитані байти за ідентифікатором.

Ідентифікатор блоба в маніфесті мусить складатися з 64 символів з набору `0`-`9` і `a`-`f`. Будь-що інше не є ідентифікатором блоба, і еталонна реалізація відхиляє такий маніфест.

Еталонний читач не гешує байти блоба, коли відкриває бандл або коли копіює один з них назовні. Він перевіряє, що елемент існує. Крок інсталяції перевіряє геш, коли перевіряє кожен артефакт, хіба що викликач вимкнув цю перевірку.

### Відхилення бандла {#refusing-a-bundle}

Читач мусить відхилити бандл, чий маніфест називає блоб, якого бандл не містить, і мусить зробити це, перш ніж щось із нього встановлювати. Перевірка полягає в тому, що zip має елемент з іменем `blobs/<id>` для кожного ідентифікатора блоба, який називає `source` артефакта.

Еталонний читач виконує цю перевірку, коли відкриває бандл, тому відсутній блоб виявляється ще до першого завантаження чи копіювання. Читання лише заголовка цієї перевірки не виконує, бо воно ніколи не читає список артефактів.

Записувач не повинен писати блоб, чиї байти не гешуються в його ім’я. Еталонний записувач гешує кожен блоб, коли копіює його в zip, і відхиляє бандл, якщо геш відрізняється.

## Детермінованість {#determinism}

Еталонний записувач видає ті самі байти для тих самих маніфеста й блобів:

- кожен елемент має мітку часу 1980-01-01 00:00:00, тобто типове значення zip, а не час збирання;
- кожен елемент має режим Unix `0644`;
- елементи записуються в наведеному вище порядку.

Під час читання ніщо від цього не залежить. Два бандли того самого маніфеста відрізняються, лише якщо відрізняються їхні маніфести або блоби. Стиснуті байти deflate-елемента залежать від реалізації deflate, тому порівнюйте два бандли за вмістом їхніх елементів, а не за байтами самого zip-файла.

## Деталі zip {#zip-details}

Вони описують еталонний записувач.

- Елемент розміром від 4 ГіБ записується з Zip64, тому читач, який має відкривати такий, мусить підтримувати Zip64.
- Він не задає коментар архіву й не вмикає шифрування, а також не пише дескриптори даних: розміри й CRC кожного елемента лежать у його локальному заголовку.
- Імена є наведеними вище іменами елементів, з `/` як роздільником. Елементів каталогів він не пише.

## Читання бандла {#reading-a-bundle}

Читач, якому потрібен увесь маніфест:

```text
open the file as a zip
for name in ["opys.json", "artifacts.json"]:
    if the zip has no entry name: refuse ("not a bundle")
head = parse_json(read(zip, "opys.json"))
if head.format is not the integer 1: refuse ("unknown format")
vars      = head.vars or {}
launch    = head.launch          (absent is fine)
restrict  = head.restrict        (absent is fine)
artifacts = parse_json(read(zip, "artifacts.json"))
for each artifact whose source has a "blob" field:
    id = source.blob
    if id is not 64 lowercase hex digits: refuse
    if the zip has no entry "blobs/" + id: refuse ("names a blob nothing holds")
return the manifest

later, when installing the artifact that names blob id:
    copy entry "blobs/" + id to the artifact's path
    if the sha256 of the copied bytes is not id: refuse (the bundle is corrupt)
```

Крок розбору в еталонному читачі перевіряє `format` першим і лише потім розбирає решту заголовка, з причини, наведеної в розділі [Поле format](#the-format-field).

## Читання лише заголовка {#reading-the-head-alone}

Заголовок є першим елементом бандла, який записав еталонний записувач, тому каталог zip для його читання не потрібен. Перевіряйте кожне поле, перш ніж на нього покладатися.

```text
read 30 bytes at offset 0
if they do not start with the local file header signature 50 4b 03 04: refuse
method   = bytes 8-9   (little-endian u16); must be 0 (stored)
flags    = bytes 6-7   (little-endian u16); bit 0x0008 must be clear
csize    = bytes 18-21 (little-endian u32); the stored size
name_len = bytes 26-27 (little-endian u16)
extra    = bytes 28-29 (little-endian u16)
name     = the name_len bytes after offset 30; must be "opys.json"
data     = csize bytes starting at offset 30 + name_len + extra
parse data as JSON and check format, as above
```

Якщо будь-яка з цих перевірок не проходить, прочитайте замість цього каталог zip і знайдіть елемент за іменем. Бандл від іншого записувача може використовувати дескриптор даних, стиснутий заголовок або додаткове поле, які цей нарис не враховує.

Еталонна реалізація читає заголовок через каталог zip, тому це коштує каталог і заголовок, скільки б не важив бандл. У будь-якому разі список артефактів ніколи не читається.

## Сеанс з unzip {#a-session-with-unzip}

Цей скрипт пише малий бандл: один блоб, одне завантаження і команду запуску. Блобом є п’ять байтів `hello`.

```js
import { blobBytes, blobId, decodeManifest, writeBundle } from '@opys/core';

const hello = Buffer.from('hello');
const id = blobId(hello);

const manifest = decodeManifest({
  vars: { root: '/srv/game' },
  artifacts: [
    { path: '${root}/config/hello.txt', source: { blob: id }, size: 5 },
    {
      path: '${root}/libraries/a/a-1.0.jar',
      source: { url: 'https://example.com/a-1.0.jar' },
      integrity: { sha1: 'da39a3ee5e6b4b0d3255bfef95601890afd80709' },
    },
  ],
  launch: {
    command: '/usr/bin/java',
    workdir: '${root}',
    args: ['-cp', '${root}/libraries/a/a-1.0.jar', 'com.example.Main'],
  },
});

await writeBundle('out.opys', manifest, { [id]: blobBytes(hello) });
```

Покажіть його вміст:

```sh
unzip -lv out.opys
```

```text
Archive:  out.opys
 Length   Method    Size  Cmpr    Date    Time   CRC-32   Name
--------  ------  ------- ---- ---------- ----- --------  ----
     248  Stored      248   0% 01-01-1980 00:00 d7474483  opys.json
     285  Defl:N      201  30% 01-01-1980 00:00 cf6b63d1  artifacts.json
       5  Defl:N        7 -40% 01-01-1980 00:00 3610a686  blobs/2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
--------          -------  ---                            -------
     538              456  15%                            3 files
```

Прочитайте заголовок, тільки заголовок:

```sh
unzip -p out.opys opys.json | head -4
```

```text
{
  "format": 1,
  "vars": {
    "root": "/srv/game"
```

Скопіюйте один блоб назовні та звірте його з іменем:

```sh
unzip -p out.opys blobs/2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824 \
  | sha256sum
```

```text
2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824  -
```

Перевірте власні CRC zip:

```sh
unzip -t out.opys | tail -1
```

```text
No errors detected in compressed data of out.opys.
```

`unzip -t` перевіряє власні CRC zip. Назв блобів вона не перевіряє. Рядок з `sha256sum` вище є перевіркою, яка це робить.

## Ім’я файла {#the-file-name}

Типово бандл називається `<name>.opys`. Поле конфігурації `output` називає файл, який пише `opys build`, а в прикладах використано `game.opys`. Від розширення у форматі ніщо не залежить, і еталонний читач відкриває бандл під будь-яким іменем. Лаунчер може вирішувати за розширенням, що відкривати; сам формат цього не робить.
