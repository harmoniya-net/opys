# Написання плагіна

Ця сторінка призначена для JavaScript-розробника, який хоче власний плагін у файлі `opys.config.mjs`, а не один з `@opys/minecraft`. Ви збудуєте малий плагін крок за кроком: спершу змінну, потім файл з URL, потім згенерований файл, потім аргумент запуску. Готова конфігурація наведена після кроку 4.

Плагін є звичайним об’єктом. Вам не потрібні базовий клас, крок реєстрації чи будь-що від opys понад помічники з `@opys/dev` і `@opys/core`.

## Контракт {#the-contract}

Плагін має `name` і функцію `build`:

```ts
interface OpysPlugin {
  name: string;
  build(ctx: BuildContext): Promise<Contribution> | Contribution;
}

interface BuildContext {
  log: (scope: string, message: string) => void;
  configDir: string;
  mode: string;
}

interface Contribution {
  artifacts?: Artifact[];
  blobs?: Blobs;
  vars?: ValDefs;
  launch?: Record<string, Valset | Val | string>;
  envs?: ValDefs;
}
```

`build` повертає `Contribution`, і кожне його поле необов’язкове:

| Поле        | Що воно додає в маніфест                                                                          |
| ----------- | ------------------------------------------------------------------------------------------------- |
| `artifacts` | Файли для завантаження, копіювання чи розпакування, кожен зі шляхом і джерелом.                   |
| `blobs`     | Де на вашій машині лежать байти блоб-артефактів цього плагіна.                                    |
| `vars`      | Змінні, які визначає маніфест, наприклад `motd` з кроку 1.                                        |
| `launch`    | Іменовані частини команди запуску для `command` і `args` вашої конфігурації.                      |
| `envs`      | Змінні середовища, які запущена гра отримує типово. `manifest.envs` з конфігурації їх перекриває. |

`BuildContext` має три поля:

- `log(scope, message)` друкує рядок під час збирання. CLI показує його як `[scope] message`, тому передавайте ім’я вашого плагіна як область.
- `configDir` є абсолютним каталогом файла конфігурації. Розв’язуйте шляхи, які ви читаєте з диска, відносно нього, а не відносно робочого каталога.
- `mode` є значенням прапорця `--mode`. Коли прапорець не задано, CLI передає ім’я команди (`build`, `install` або `launch`).

### Чиста конструкція, введення і виведення в `build` {#pure-to-construct-i-o-in-build}

Виклик конструктора вашого плагіна не мусить виконувати жодної роботи. Він повертає об’єкт, а рушій викликає `build` пізніше, один раз на збирання. Кожен мережевий запит, читання файла й геш належать всередину `build`. Саме це дозволяє конфігурації імпортувати модуль плагіна без побічних ефектів.

Плагіни працюють лише під час збирання. Лаунчер ніколи не викликає `build`, тому все, що потрібно плагіну під час запуску, має лежати в його `Contribution`.

## Крок 1: змінна {#step-1-a-variable}

Почніть з найменшого плагіна, який щось робить. Він дає одну змінну і більше нічого:

```js
import { definePlugin } from '@opys/dev';

const welcome = (motd) =>
  definePlugin({
    name: 'welcome',
    build(ctx) {
      ctx.log('welcome', `motd is "${motd}"`);
      return { vars: { motd } };
    },
  });
```

`vars` є відображенням імені у значення, і будь-який шлях артефакта чи аргумент запуску може посилатися на нього як `${motd}`. Змінну повинен задавати лише той плагін, який її визначає; див. [Імена та власники](#names-and-owners) нижче.

`definePlugin` повертає новий об’єкт з вашими `name` і `build` та приєднаними ланцюжковими методами. Жодна інша властивість об’єкта, який ви передаєте, не переноситься. Звичайний об’єкт `{ name, build }` теж працює, якщо ці методи вам не потрібні. Вони описані [нижче](#overrides-with-selectors).

## Крок 2: файл з URL із зафіксованим гешем {#step-2-a-file-from-a-url-with-a-pinned-hash}

Артефакт каже, куди потрапляє файл (`path`), звідки він береться (`source`) і яким мусить бути його геш (`integrity`). Цей артефакт завантажує jar бібліотеки:

```js
build(ctx) {
  ctx.log('welcome', `motd is "${motd}"`);
  return {
    vars: { motd },
    artifacts: [
      {
        path: '${root}/downloads/brigadier-1.3.10.jar',
        source: {
          url: 'https://libraries.minecraft.net/com/mojang/brigadier/1.3.10/brigadier-1.3.10.jar',
        },
        size: 80082,
        integrity: { sha1: 'd15b53a14cf20fdcaa98f731af5dda654452c010' },
      },
    ],
  };
},
```

- `path` є шаблоном. `${root}` є значенням під час запуску; конфігурація постачає його в `runClient`, як це робить приклад. Див. [Значення під час запуску](/uk/guide/run-client).
- `integrity` є гешем, який інсталятор перевіряє після завантаження. Це один з `sha1`, `sha256` або `md5`, і це може бути список таких об’єктів. Кладіть по одному гешу в кожен об’єкт: об’єкт з двома зберігає лише один. Поле `size` необов’язкове.
- Артефакт приймає `path`, `source`, `size`, `rules`, `integrity`, `metadata` і `extract`. Будь-який інший ключ провалює збирання.
- Збирання файл не завантажує. Воно записує URL і геш, які ви написали, тому геш мусить бути справжнім. Завантаження з ним звіряє саме інсталятор.

## Крок 3: згенерований файл як блоб {#step-3-a-generated-file-as-a-blob}

Деякі файли не мають URL: конфігурація, яку пише ваш плагін, або файл, який ви тримаєте в себе. Вони подорожують всередині бандла як **блоби**. Блоб називається за sha256 його байтів, тому артефакт називає блоб і ніколи не називає розташування:

```js
import { blobBytes, blobId, sourceBlob } from '@opys/core';

build(ctx) {
  // ...артефакт з URL із кроку 2...
  const config = new TextEncoder().encode(`motd = "${motd}"\n`);
  const id = blobId(config);
  return {
    vars: { motd },
    artifacts: [
      // ...артефакт з URL...
      { path: '${root}/config/welcome.toml', source: sourceBlob(id) },
    ],
    blobs: { [id]: blobBytes(config) },
  };
},
```

Три частини виконують три завдання:

- `blobId(bytes)` повертає шістнадцятковий sha256 байтів. Це ім’я.
- `sourceBlob(id)` створює `source` артефакта, `{ blob: id }`.
- `blobs` відображає кожен ідентифікатор на місце його байтів на цій машині. `blobBytes` тримає згенеровані вами байти; `blobFile(path)` вказує на файл на диску. Ідентифікатор і розмір файла на диску повертає `hashBlobFile(path)` як обіцянку обох.

Артефакт блоба не має власної `integrity`. Ім’я є гешем, і інсталятор звіряє з ним байти. Блоб, якого не називає жоден артефакт, у бандл не потрапляє; рушій його відкидає.

::: tip Файли на диску
Для каталога файлів вам не потрібно писати це вручну. Помічник `files` з `@opys/dev` бере на себе гешування й розміщення. Див.
[files](/uk/plugins/files).
:::

## Крок 4: група запуску, використана з `args` {#step-4-a-launch-group-used-from-args}

Плагін не може вибрати команду запуску. Він може запропонувати її частини, а порядок вирішує конфігурація. Кожен ключ `launch` є іменованою групою, і конфігурація читає її за іменем плагіна:

```js
build(ctx) {
  // ...усе з кроку 3...
  return {
    vars: { motd },
    artifacts: [/* ... */],
    blobs: { [id]: blobBytes(config) },
    launch: { jvmArg: '-Dwelcome.motd=${motd}' },
  };
},
```

У конфігурації групи плагіна приходять під ключем з його іменем:

```js
manifest: {
  command: ({ java }) => java.bin,
  args: ({ welcome, minecraft }) => [
    welcome.jvmArg,
    minecraft.jvmArgs,
    minecraft.mainClass,
    minecraft.gameArgs,
  ],
  workdir: '${game_directory}',
},
```

Значенням групи може бути рядок, `Val` або список `Val`, залежно від того, що потрібно `args` конфігурації. `Val` є рядком або об’єктом `{ rules, value }` для аргумента, який діє лише там, де діють його правила.

Збирання фрагмент `${motd}` у рядку не розгортає; він розгортається під час запуску зі змінних, які визначає маніфест. Групи запуску існують лише для живлення функцій конфігурації `command`, `args`, `workdir` і `envs`. У бандл вони не записуються; туди потрапляють аргументи, які повертають функції.

## Перевизначення із селекторами {#overrides-with-selectors}

Кожен метод плагіна повертає **новий** плагін з ще однією зміною його артефактів. Оригінал лишається недоторканим, тому ланцюжок читається зліва направо:

| Метод                       | Що він робить                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `exclude(match)`            | Відкидає кожен артефакт, що збігається.                                                                                                                                        |
| `addRule(match, rules)`     | Додає набір правил до `rules` кожного артефакта, що збігається. Набір тримається, лише якщо тримається кожне правило в ньому, тому артефакт далі діє в меншій кількості місць. |
| `removeIntegrity(match)`    | Очищає `integrity` в артефактах, що збігаються, тому вони встановлюються без перевірки.                                                                                        |
| `updateFirst(match, patch)` | Неглибоко зливає `patch` у перший артефакт, що збігається.                                                                                                                     |
| `updateMany(match, patch)`  | Неглибоко зливає `patch` у кожен артефакт, що збігається.                                                                                                                      |

Вони змінюють лише `artifacts`. Поля `vars`, `launch`, `blobs` і `envs` проходять без змін.

`match` є **селектором**. Це одна з трьох речей:

- рядок з glob-шаблоном, який зіставляється зі шляхом артефакта (наприклад `'**/*.jar'`);
- масив рядків з glob-шаблонами, який збігається, якщо збігається будь-який з них;
- предикат `(artifact) => boolean` для всього іншого, наприклад для виду джерела.

Параметр `rules` приймає той самий скорочений запис, що й маніфест, наприклад `'allow.os.linux'`.
Параметр `patch` є або об’єктом з полями для встановлення, або функцією від зіставленого артефакта, яка такий об’єкт повертає.

```js
const pack = welcome('Hello')
  .addRule('**/brigadier-*.jar', 'allow.os.linux')
  .exclude((a) => 'blob' in a.source);
```

Перший виклик додає правило лише для Linux до jar з кроку 2. Другий відкидає кожен артефакт, чиє джерело є блобом, а тут це згенерований файл. Ланцюжкові методи виконуються по черзі над артефактами, які повернув `build` плагіна.
Предикат отримує кожен артефакт у тому вигляді, як його пише маніфест, тому `'url' in a.source` істинне для URL, а `'blob' in a.source` для блоба.

Glob-шаблон зіставляється зі шляхом у тому вигляді, як ви його написали, з нерозгорнутими `${root}` та іншими посиланнями, а `{` і `}` означають у шаблоні чергування. Тому починайте взірець з `**/`, а не називайте в ньому `${root}`. Синтаксис glob описано в [@opys/core](/uk/plugins/core#globs).

## Імена та власники {#names-and-owners}

Ім’я плагіна `name` робить дві речі, тому вибирайте його уважно:

- Це ключ, за яким конфігурація знаходить групи запуску плагіна, тому `name: 'welcome'` робить `welcome.jvmArg` доступним для `args`. Два плагіни з тим самим іменем перезаписують групи один одного. Використовуйте ім’я, яке є правильним ідентифікатором JavaScript, щоб його можна було деструктурувати.
- Це власник, показаний у попередженнях.

Область рядка журналу це те, що ви передаєте в `ctx.log`. Використовуйте там теж ім’я плагіна, щоб читач бачив, чий це рядок.

Змінні мають по одному власнику. Коли ту саму змінну задають два плагіни, перемагає пізніший у `plugins`, а збирання друкує попередження:

```
[opys] warning: var 'motd' set by both 'welcome' and 'other' — using 'other'
```

Змінні середовища з `envs` дотримуються того самого правила й друкують схоже попередження. Артефакти дотримуються його за шляхом: коли два артефакти мають той самий шлях, пізніший замінює раніший, спершу в порядку плагінів, а потім `manifest.artifacts`, без попередження.

Лише один плагін має володіти змінною. Наприклад, тільки `java` задає `java_home`.
Називайте ваші змінні за вашим плагіном, щоб вони не могли зіткнутися з чужими. Якщо змінну хоче задати сама конфігурація, `manifest.vars` є шаром перевизначень, і він мовчазний; значення конфігурації перемагає без попередження.

## Правила доброго плагіна {#rules-for-a-good-plugin}

- **Визначайте все під час збирання.** Маніфест повністю визначений. Він ніколи не каже «остання версія» або «спитай цей сервер, який файл». З’ясуйте версію, URL і геш всередині `build` і запишіть конкретні значення у внесок.
- **Фіксуйте кожен геш.** Дайте кожному URL-артефакту `integrity`, а блоби нехай називаються за своїм гешем. Артефакт без геша є файлом, який інсталятор не може перевірити.
- **Ніколи не читайте машину запуску.** `build` працює на машині, яка робить бандл. Такий шлях, як `userDataDir(...)`, `os.homedir()` або значення з `process.env`, описує ту машину, і він запікається в маніфест для кожного гравця, який його встановить. Значення для конкретної машини належать у `runClient` або в `--var`, де їх постачає машина запуску.
- **Тримайте секрети поза маніфестом.** Бандл є файлом, який отримують інші люди. Токен доступу чи пароль ніколи не потрапляють у `vars`, блоб чи групу запуску.
- **Використовуйте помічники для файлів, які ви вже маєте.** `files` покриває каталог на вашому диску, а `links` покриває вже опублікований файл на GitHub, GitLab, Modrinth, CurseForge чи за будь-яким URL. Вони фіксують те, що додають. Див. [Моди та файли](/uk/guide/mods).
