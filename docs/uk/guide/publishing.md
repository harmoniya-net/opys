# Публікація бандла

Ця сторінка про те, що відбувається після `opys build`: що містить файл, як його розмістити, як гравці отримують кожне оновлення і чому тут не місце. Вона для автора модпака. Сторона лаунчера описана в розділі [Вбудовування рантайму](/uk/launcher/embedding).

## Збирання бандла {#build-the-bundle}

```sh
opys build
```

Команда читає `opys.config.mjs`, запускає кожен плагін і записує файл, названий полем `output` (`game.opys` у прикладах). Відносний `output` розкривається від каталогу файлу конфігурації. Прапор `-o` перекриває його, а відносний `-o` розкривається так само. Останній рядок каже, що записано:

```text
Written to game.opys (<artifacts> artifact(s), <blobs> blob(s))
```

Якщо вихід ніде не названо, `opys build` замість цього друкує маніфест як JSON. Це вигляд для читання та порівняння. Блоби до нього не входять, тому встановити з нього нічого не можна.

Бандл є zip-архівом з трьома видами елементів:

| Елемент          | Містить                                                                           |
| ---------------- | --------------------------------------------------------------------------------- |
| `opys.json`      | Заголовок: `format`, `vars`, `launch`, `restrict`. Перший елемент, без стиснення. |
| `artifacts.json` | Список артефактів: по одному запису на файл, який інсталяція розміщує.            |
| `blobs/<sha256>` | По одному елементу на вміщений файл, названому за хешем його байтів.              |

Точна розкладка описана в розділі [про формат бандла](/uk/reference/bundle-format). Оскільки це звичайний zip, команда `unzip -l game.opys` показує його вміст, а `unzip -p game.opys opys.json` друкує заголовок.

## Збирання детерміноване {#the-build-is-deterministic}

Дві збирання тієї самої конфігурації дають ті самі байти. Записувач ставить кожному елементу ті самі мітку часу й режим, пише блоби за порядком ідентифікаторів і звіряє хеш кожного блоба з його ім’ям під час запису.

Ця гарантія стосується записувача, а не плагінів. Плагін, який під час збирання визначає рухливу ціль, наприклад `forge('1.20.1')`, що вибирає найкращу збірку, опубліковану цього дня, може дати інший маніфест у пізнішій збиранні. Саме ця різниця і доносить оновлення до гравців.

## Розміщення на будь-якому статичному сервері {#host-it-on-any-static-server}

Бандл є одним файлом, тому підійде будь-який сервер, який віддає байти у відповідь на GET. Відповідь з кодом поза 2xx рантайм вважає помилкою. Лаунчер, який вбудовує `@opys/runtime`, приймає URL напряму:

```ts
import { launch } from '@opys/runtime';

const child = await launch(
  { url: 'https://example.com/packs/game.opys' },
  {
    vars: {
      root: '/home/player/.my-pack',
      username: 'Player',
      uuid: '00000000-0000-0000-0000-000000000001',
      token: '0',
    },
  },
);
```

Джерело `url` завантажується цілком, у тимчасовий файл, перш ніж з нього щось встановлюється. Щоразу, коли джерело визначається, воно завантажується знову.

Команда `opys` не приймає URL. `opys launch` читає бандл за шляхом, тому гравець, який користується командним рядком, спершу завантажує файл:

```sh
curl -fLO https://example.com/packs/game.opys
opys launch game.opys --var root=$HOME/.my-pack --var username=Player \
  --var uuid=00000000-0000-0000-0000-000000000001 --var token=0
```

::: warning Крок встановлення завантажувача
Коли аргументи запуску в бандлі називають horno, процесори завантажувача мають один раз відпрацювати на машині гравця. horno робить це як частину командного рядка гри, тому запустити гру достатньо. `install()` в `@opys/runtime` лише розміщує файли. Лаунчер, який хоче виконати процесорів до того, як гравець натисне кнопку гри, має сам виконати цей крок так, як це робить `opys install`. Як саме, пояснює розділ [Встановлення і запуск](/uk/launcher/embedding#loader-install-steps).
:::

## Оновлення {#updates}

Щоб оновити модпак, перезберіть бандл і замініть файл за тим самим URL. Наступного разу, коли лаунчер гравця визначить бандл, він зробить таке:

1. Завантажить новий бандл цілком.
2. Для кожного артефакту порахує хеш файла, який уже є на диску. Файл, що досі збігається зі своїм хешем, пропускається. Файл, якого бракує або який змінився, завантажується у `<path>.partial` і перейменовується на своє місце.
3. Перевірить завантажені файли за їхніми хешами.
4. Розпакує кожен артефакт архіву. Розпакування працює при кожному встановленні, тому розпаковані файли завжди відповідають маніфесту.
5. Виконає прибирання, якщо бандл має `restrict` (див. нижче).

Артефакт без хеша ніколи не завантажується повторно, якщо його файл уже існує. Кожен артефакт, який створюють `files` і `links`, має хеш, тому це стосується лише артефактів, які ви написали вручну без нього.

### Видалення файлів: `restrict` {#removing-files-restrict}

Прибирання видаляє не все, що новий маніфест опустив. Воно видаляє лише файли, що збігаються з glob-шаблоном `restrict`. Файл, який не покриває жоден шаблон, залишається на місці.

```js
manifest: {
  // ...
  restrict: ['${game_directory}/mods/*.jar'],
},
```

Прибирання працює так:

- Кожен шаблон інтерполюється зі значеннями змінних під час встановлення, тому `${game_directory}` будується з `root`, який дала машина запуску.
- Каталог, що прибирається, це шлях шаблону до останнього `/` перед першим символом підстановки (`*`, `?`, `{` або `[`). Шаблон без такого каталогу, наприклад `*.jar`, не прибирає нічого.
- Кожен файл під цим каталогом, що збігається з шаблоном і не є артефактом цього маніфесту, видаляється. `*` і `?` збігаються в межах одного рівня каталогу, `**` збігається крізь рівні, а `{a,b}` вибирає між варіантами, тому шаблон вище залишає jar у підпапці `mods/` недоторканим.
- Далі видаляється кожен порожній підкаталог під цим каталогом, незалежно від того, чи збігся шаблон хоч з чимось у ньому.

::: warning Пишіть шаблон так само, як шляхи артефактів
Прибирання порівнює шляхи як рядки, коли змінні в них уже підставлено. `game_directory` дорівнює `${root}/` із завершальним слешем, тому `${game_directory}/mods/a.jar` стає `…/root//mods/a.jar`, а `${root}/mods/a.jar` стає `…/root/mods/a.jar`. Вони називають той самий файл, але є різними рядками. Шаблон, написаний в одному варіанті, не впізнає артефакт, написаний в іншому, і змете артефакт як зайвий. Використовуйте в `restrict` ту саму змінну, що й у шляхах артефактів, які він захищає.
:::

Прибирання працює останнім, після розпакування, і лише коли встановлення до нього дійшло. Звідси випливають два наслідки. Glob-шаблон `restrict` не має покривати місце, куди пише правило `extract`: прибирання не знає про файли, які туди поклав архів, тому воно видалить те, що розпакування щойно записало. А мод, прибраний з `mods/`, видаляється при наступному встановленні у гравця, лише якщо якийсь шаблон називає `mods/`.

## Варіанти збирання через `--mode` {#build-variants-with-mode}

Параметр `--mode` задає `mode`, який отримує функція конфігурації. Він відрізняє збирання для розробки від продуктової:

```js
export default defineConfig(({ mode }) => {
  const dev = mode === 'dev';
  return {
    output: dev ? 'game-dev.opys' : 'game.opys',
    plugins: [
      forge('1.20.1'),
      java('17'),
      ...(dev
        ? [files({ from: 'dev-mods', to: '${game_directory}/mods/${rel}' })]
        : []),
    ],
    manifest: {
      // ... те саме, що й у продуктовій конфігурації
    },
  };
});
```

```sh
opys build --mode dev          # записує game-dev.opys
opys build                     # записує game.opys
```

Коли `--mode` не задано, `mode` дорівнює імені команди: `build`, `install` або `launch`. Порожнім рядком він не буває ніколи. Порівнюйте з `mode === 'dev'`, як показано вище, щоб типово вибиралася продуктова гілка.

`opys launch --mode dev` збирає варіант у пам’яті та запускає його. Бандл не має конфігурації, тому `opys launch game.opys` не має режиму на вибір.

## Чому тут не місце {#what-stays-out-of-a-bundle}

Бандл є даними, і кожен, хто має файл, може прочитати його цілком. Тримайте звідси далі таке.

| Не кладіть у бандл                                                 | Кладіть сюди                            | Чому                                                                                                |
| ------------------------------------------------------------------ | --------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Шляхи з машини збирання, такі як `userDataDir()` або `/home/you/…` | `runClient` або `--var` під час запуску | Бандл один для всіх гравців, тому ваш шлях розійдеться до них усіх.                                 |
| Ім’я користувача, UUID або токен доступу                           | `runClient` або `--var` під час запуску | Значення надаються на машині запуску щоразу, коли вона стартує.                                     |
| Ключі чи паролі будь-якого виду                                    | Нікуди в бандлі                         | `manifest.vars`, `command`, `args`, `envs` і `restrict` лежать в `opys.json`, а це звичайний текст. |
| Таємні файли через `files`                                         | Нікуди в бандлі                         | Вміщений файл є стисненим елементом zip. `unzip` видобуде його для будь-кого.                       |

Значення з `--var` ніколи не записуються в бандл. Вони застосовуються лише на машині запуску.

## Вміщені файли або файли на хостингу {#carried-files-or-hosted-files}

`files({ from, to })` без `url` несе кожен файл у бандлі. З `url` кожен файл вказує на копію, яку ви розмістили, і фіксується за її хешем:

```js
files({ from: 'mods', to: '${game_directory}/mods/${rel}' }); // вміщені
files({
  from: 'mods',
  to: '${game_directory}/mods/${rel}',
  url: 'https://cdn.example.com/mods/${rel}',
}); // на хостингу, зафіксовані за sha1
```

Вибір змінює розмір бандла і вартість оновлення:

|                                                         | Вміщені (без `url`)                                                                     | На хостингу (`url`)                                                |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Розмір бандла                                           | Зростає на розмір кожного файла                                                         | Один рядок на файл в `artifacts.json`                              |
| Хостинг                                                 | Самого бандла достатньо                                                                 | Кожен файл за своїм URL, доступний, доки він потрібен гравцям      |
| Вартість кожного запуску, коли лаунчеру дано URL бандла | Весь бандл завантажується, включно з вміщеними файлами, навіть коли нічого не змінилося | Лише бандл. Змінений файл завантажується, незмінний лише хешується |
| Зафіксовано за                                          | sha256 в імені блоба                                                                    | `hash: 'sha1'` (типово) або `'sha256'`                             |

Вміщені файли є простим вибором. Жодному іншому серверу не треба лишатися вгорі, і ніщо не може застаріти. Розміщення файлів на хостингу виправдовується, коли файли великі й рідко змінюються, бо гравці завантажують лише ті, що змінилися. Моди з Modrinth і CurseForge краще називати через [`modrinth`](/uk/plugins/modrinth) і [`curseforge`](/uk/plugins/curseforge), які фіксують їх, нікуди їх не копіюючи. Докладніше в розділі [Моди та файли](./mods).

::: tip Перевірте розмір перед публікацією
Команда `ls -l game.opys` показує, що гравці завантажуватимуть при кожному запуску. Якщо файл більший, ніж ви чекали, причина майже завжди у вміщеному файлі, який можна було б розмістити на хостингу.
:::
