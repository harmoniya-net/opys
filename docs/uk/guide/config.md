# Файл конфігурації

Ця сторінка описує кожне поле `opys.config.mjs`, модуля, який читають
`opys build` і `opys launch`. Вона для авторів модпаків: що робить кожне поле,
як поєднуються внески плагінів і куди значенню не можна потрапляти.

Конфігурація це звичайний модуль JavaScript. Її типовий експорт походить із
`defineConfig`, який повертає свій аргумент без змін і існує для того, щоб ваш
редактор міг перевірити структуру. Ось повна конфігурація, яка збирається і

## Структура {#the-shape}

| Поле        | Тип     | Призначення                                                                  |
| ----------- | ------- | ---------------------------------------------------------------------------- |
| `output`    | рядок   | Куди `opys build` записує бандл. Необов’язкове.                              |
| `plugins`   | список  | Плагіни, чий вихід складає інсталяцію.                                       |
| `manifest`  | об’єкт  | Як її запускати, і все буквальне, що треба додати.                           |
| `runClient` | функція | Значення під час запуску, застосовуються при кожному запуску. Необов’язкова. |

`manifest` приймає поля з таблиці нижче. Обов’язкові лише `command` і `args`.

| Поле        | Тип                  | Призначення                                                      |
| ----------- | -------------------- | ---------------------------------------------------------------- |
| `command`   | функція              | Програма для запуску. Обов’язкове.                               |
| `args`      | функція              | Аргументи в тому порядку, у якому ви їх перелічите. Обов’язкове. |
| `workdir`   | рядок або функція    | Робочий каталог. Типово `.`.                                     |
| `envs`      | об’єкт або функція   | Змінні середовища для гри.                                       |
| `vars`      | об’єкт               | Змінні часу збирання, запікаються в бандл.                       |
| `artifacts` | список               | Буквальні файли для додавання в інсталяцію.                      |
| `restrict`  | список glob-шаблонів | Файли для вилучення після встановлення.                          |

## Об’єкт або функція {#object-or-function}

`defineConfig` приймає або саму конфігурацію, або функцію, яка її повертає:

```js
export default defineConfig(({ mode }) => ({
  // ...
}));
```

Функційна форма отримує одне значення, `mode`. Це значення
`opys build --mode <m>` (або `opys launch --mode`, `opys install --mode`).
Коли ви не передаєте `--mode`, `mode` це назва команди, яка виконується:
`build`, `install` або `launch`. Використовуйте його, щоб одна конфігурація
давала дві інсталяції:

```js
export default defineConfig(({ mode }) => {
  const release = mode === 'release';
  return {
    // плагіни і маніфест можуть читати `release` тут
  };
});
```

Функція також може повертати проміс, тож конфігурація встигає прочитати файли
або звернутися до мережі, перш ніж оголосити свої плагіни.

opys читає `opys.config.mjs` з поточного каталогу, якщо ви не передасте
`-i <file>`. Каталог із конфігурацією це якір для відносних шляхів, таких як
`from` у `files`.

## output {#output}

`output` це шлях до бандла, який записує `opys build`. Відносний шлях
відлічується від каталогу конфігурації. За домовленістю це `<name>.opys`.
`opys build -o <path>` перекриває його.

`opys launch` ігнорує `output`. Він збирає маніфест у пам’яті й ніколи не
записує бандл.

## plugins {#plugins}

`plugins` це плаский список. Ролей немає, і ніщо не перевіряє, скільки
плагінів кожного виду у вас є: список лише каже, з чого складається
інсталяція, і більше нічого.

```js
plugins: [
  minecraft('1.21.1'),
  java('21'),
  files({ from: 'mods', to: 'mods/${rel}' }),
],
```

Усі плагіни збираються водночас. Далі їхній вихід згортається в маніфест у
порядку списку, і саме порядок вирішує результат, коли два плагіни
розходяться. Поєднуються три речі, а четверта передається далі:

**Артефакти** з’єднуються в порядку плагінів, а далі йдуть буквальні
`manifest.artifacts`. Два артефакти з тим самим шляхом це один артефакт:
пізніший перемагає, а шлях зберігає позицію своєї першої появи. Шляхи
порівнюються після нормалізації, тож `mods/a.jar` і `./mods//a.jar` це той
самий шлях.

**Змінні** поєднуються в порядку плагінів, і пізніший плагін перемагає. Якщо
два різні плагіни задають те саме ім’я, збирання друкує попередження і лишає
пізніше значення:

```text
[opys] warning: var 'NAME' set by both 'FIRST' and 'LAST' — using 'LAST'
```

`NAME` це змінна, а `FIRST` і `LAST` це два плагіни в тому порядку, у якому
вони стоять у списку. У повідомленні для envs на місці `var` стоїть `env`.

Це попередження про випадок зіткнення, якого ви не планували. Щоб свідомо
розв’язати його, задайте ім’я в `manifest.vars` (або `manifest.envs`), яке
застосовується мовчки.

**Envs** підпорядковуються тому самому правилу, що й змінні, з тим самим
попередженням. Плагін використовує їх для типових значень: `java` експортує
`JAVA_HOME`, тож гра має його без вашого прохання. `manifest.envs` це останній
шар, він перекриває їх.

**Групи запуску** це названі частини, які плагін пропонує для командного
рядка, наприклад `jvmArgs`, `mainClass` і `gameArgs` від завантажувача або
`bin` від `java`. Вони не поєднуються. Їх отримують ваші функції `command` і
`args`, описані далі.

Ім’я плагіна це його ключ у тих функціях, і попередження про зіткнення вище
називає плагіни за ним. Давайте кожному написаному вами плагіну власне ім’я:
два з тим самим ім’ям ділять один ключ, і попередження про зіткнення між ними
ніколи не спрацьовує. Плагіни, що постачаються з opys, названо за їхньою
фабричною функцією: `minecraft`, `forge`, `java`, `files`, `links` тощо.

## manifest.command, args, workdir {#manifest-command-args-workdir}

`command` і `args` це функції, а `workdir` і `envs` можуть бути або простим
значенням, або функцією. Функція отримує `PluginMap`: об’єкт за іменами
плагінів, чиї значення це групи запуску того плагіна. Потрібні частини ви
читаєте за ім’ям:

```js
manifest: {
  command: ({ java }) => java.bin,
  args: ({ minecraft }) => [
    minecraft.jvmArgs,
    minecraft.mainClass,
    minecraft.gameArgs,
  ],
  workdir: '${game_directory}',
},
```

`command` повертає програму для запуску, зазвичай бінарний файл Java, і є
обов’язковою. `args` повертає список. Кожен елемент це рядок, одне значення
або список значень, і вони розгортаються в один рядок у тому порядку, у якому
ви їх записали. Поставте аргументи JVM перед головним класом, а аргументи гри
після нього. Порядок ваш: ніщо не сортується за роллю.

`workdir` це робочий каталог гри. Якщо ви його опустите, він дорівнюватиме
`.`. Він може бути рядком або функцією від мапи плагінів.

Ці функції виконуються під час збирання, тож вони бачать лише те, що оголошують
плагіни. Якщо вам потрібне значення, яке знає лише машина запуску, йому тут не
місце. Див. [Значення під час запуску](./run-client).

## manifest.envs {#manifest-envs}

`envs` задає змінні середовища для процесу гри. Воно приймає об’єкт або
функцію від мапи плагінів, яка повертає об’єкт:

```js
envs: { PACK_NAME: 'my-pack' },
```

Вони застосовуються поверх власних `envs` плагінів, тож ключ, заданий вами
тут, перемагає типове значення плагіна з тим самим ім’ям.

## manifest.vars {#manifest-vars}

`vars` це змінні, які маніфест задає сам для себе. Вони поєднуються поверх
змінних, оголошених плагінами, і перекривають їх без попередження.

```js
manifest: {
  vars: {
    motd: release ? 'Welcome' : 'Development build',
  },
  // ...
},
```

`manifest.vars` запікається в бандл. Кожен гравець, який встановить бандл,
отримає ті самі значення. Використовуйте його лише для констант часу
збирання, таких як мітка версії або перемикач ознак. Ніколи не кладіть сюди
шлях на вашому диску, ім’я користувача чи токен доступу: вони належать до
`runClient`, який виконується на машині запуску. На сторінці про
[значення під час запуску](./run-client) сказано, куди йде кожне з них.

## manifest.artifacts {#manifest-artifacts}

`artifacts` це список буквальних артефактів, доданих після виходу плагінів.
Артефакт це файл, потрібний інсталяції: куди він потрапляє, звідки береться і
який геш він мусить мати. Більшість авторів ніколи не пишуть його вручну.
Плагіни `files` і `links` створюють їх із каталогу на вашому диску або з
опублікованого URL. Див. [Моди та файли](./mods).

Якщо буквальний артефакт має той самий шлях, що й артефакт плагіна, він
замінює його, бо йде пізніше.

## manifest.restrict {#manifest-restrict}

`restrict` це список glob-шаблонів. Після запису інсталяції інсталятор видаляє
кожен файл, що збігається з одним із них і не є артефактом маніфеста. Так модпак
прибирає мод, який лишився від старшої версії:

```js
restrict: ['${game_directory}/mods/*.jar'],
```

Шаблони інтерполюються з тими самими змінними, що й усе інше, тож
`${game_directory}` працює. У шаблоні `*` і `?` збігаються в межах одного рівня
каталогу, `**` збігається крізь рівні, а `{a,b}` вибирає між варіантами.
Тримайте їх вузькими. Шаблон, що збігається з вашими збереженнями чи
налаштуваннями, видалить їх під час наступного встановлення.
[Публікація бандла](./publishing#removing-files-restrict) точно каже, який
каталог прибирається і коли.

## Змінні та ${name} {#variables-and-name}

Шляхи і URL артефактів, команда, аргументи, `workdir`, `envs` і `restrict`
можуть посилатися на змінні через `${name}`. Змінна це ім’я зі значенням; саме
значення може містити посилання `${other}`, які розв’язуються першими.
Інсталятор підставляє значення під час встановлення і запуску. Посилання на
ім’я, якого ніщо не визначає, лишається як написане, а циклічне посилання це
помилка. Змінні, які маніфест лишає відкритими, такі як `root` і `username`,
перелічено в [розділі Змінні](/uk/launcher/vars).

Не плутайте їх із заповнювачами `files`. `${rel}`, `${dir}` і `${filename}`
заповнюються під час збирання, один раз для кожного файла, знайденого плагіном
`files`, і вони взагалі не змінні.

## runClient {#runclient}

`runClient` це функція, яка виконується на машині запуску щоразу, коли гра
стартує. Вона отримує зібраний маніфест і повертає поля для заміни:
поверхове злиття, тож поле, яке ви повертаєте, цілком замінює те саме поле, а
решта лишається як зібрана. Саме сюди йдуть ваш кореневий каталог, ваш
обліковий запис і будь-який токен, бо вони різні для кожного гравця і не
повинні запікатися в бандл. Повний виклад у [розділі Значення під час
запуску](/uk/guide/run-client).
