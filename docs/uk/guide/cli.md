# Команда opys

Ця сторінка описує команду `opys`: її три підкоманди, два способи вказати їм інсталяцію, кожен прапор, те, що вони друкують, і коди завершення, які вони повертають. Це довідка. Спершу прочитайте розділ [Перші кроки](./getting-started), щоб побачити команду в роботі на цілому модпаку.

## Підкоманди {#subcommands}

| Команда        | Що робить                                                                                                       | Запускає гру |
| -------------- | --------------------------------------------------------------------------------------------------------------- | ------------ |
| `opys build`   | Запускає плагіни конфігурації та записує бандл                                                                  | Ні           |
| `opys install` | Завантажує, перевіряє та розпаковує все потрібне, а потім виконує крок встановлення завантажувача, якщо такий є | Ні           |
| `opys launch`  | Встановлює те, чого бракує, запускає гру і чекає, доки вона завершиться                                         | Так          |

`install` і `launch` приймають ті самі аргументи і мають спільну першу половину. `launch` дорівнює `install`, за яким іде запуск гри.

## Дві форми install і launch {#two-forms-of-install-and-launch}

`install` і `launch` приймають інсталяцію в одній із двох форм.

**З конфігурації.** Не вказуйте аргумент бандла. opys читає файл конфігурації (`opys.config.mjs`, якщо ви не назвали інший через `--input`), збирає його в пам’яті та встановлює з нього. На диск спершу нічого не записується, а файли, які несе маніфест, читаються звідти, де вони лежать. Цю форму ви використовуєте, поки пишете модпак. Функція `runClient` у конфігурації застосовується перед запуском, тому значення для конкретної машини належать саме їй.

**З бандла.** Вкажіть шлях до файла `.opys`. opys встановлює цей бандл рівно в тому вигляді, як він є. Конфігурація не читається, тому тут немає `runClient`, а значення, які знає лише машина запуску, надходять через `--var`. Цим шляхом іде розгорнутий лаунчер, і саме його варто перевірити перед публікацією.

```sh
opys launch
opys launch game.opys --var root=/path/to/install --var username=Player \
  --var uuid=00000000-0000-0000-0000-000000000001 --var token=0
```

Бандл не можна поєднувати з `--input`. opys відхилить команду, а не здогадуватиметься, що ви мали на увазі.

## build {#build}

```sh
opys build [-i opys.config.mjs] [-o game.opys] [--mode build]
```

Команда `build` читає конфігурацію, запускає кожен плагін і записує результат як бандл. Куди потрапить бандл, вирішується в такому порядку:

1. `-o` / `--output`, якщо задано.
2. Поле `output` конфігурації, якщо воно є.
3. Жодного немає: маніфест друкується до stdout як JSON.

Форма JSON є виглядом для читання та порівняння. До неї не входять файли, які несе маніфест, тому встановити з неї нічого не можна.

Відносний `--output` (або відносний `output` у конфігурації) розкривається від каталогу, що містить файл конфігурації, а не від каталогу, звідки ви запустили команду. `--input` розкривається від поточного каталогу.

У разі успіху `build` друкує один рядок до stderr:

```
Written to game.opys (412 artifact(s), 3 blob(s))
```

Поки команда працює, `build` також друкує рядки вигляду `[scope] message`: власні рядки рушія (`[opys] resolving 2 plugin(s)`, `[opys] merged N artifact(s)` і будь-яке попередження про колізію змінних) та рядки плагінів (`[java] Temurin 21.0.12.1+1`). Вони йдуть до stderr, тому коли вихід не названо, stdout містить лише JSON і нічого більше.

Команда `build` приймає лише `--input`, `--output` і `--mode`. Передавання `--var` або `--feature` є помилкою використання. Позиційний аргумент помилкою не є: `build` його ігнорує.

## install {#install}

```sh
opys install [-i opys.config.mjs] [--mode install] [--feature a,b] [--var k=v]...
opys install <bundle.opys> [--feature a,b] [--var k=v]...
```

Команда `install` робить усе те саме, що й `launch`, крім запуску гри. Вона завантажує, перевіряє та розпаковує кожен артефакт, потрібний інсталяції, а потім перевіряє, чи аргументи запуску в маніфесті називають horno. Якщо так, вона один раз виконує крок встановлення horno. Докладніше в розділі [horno та install](#horno-and-install).

Якщо маніфест не має кроку встановлення завантажувача, `install` друкує `No loader install step; everything is in place` і завершується з кодом 0. Прикладом є Forge від 1.6.1 до 1.12.2: йому такий крок не потрібен.

## launch {#launch}

```sh
opys launch [-i opys.config.mjs] [--mode launch] [--feature a,b] [--var k=v]...
opys launch <bundle.opys> [--feature a,b] [--var k=v]...
```

Команда `launch` виконує те саме встановлення, що й `install`, а потім запускає гру і друкує її ідентифікатор процесу:

```
Launching...
 PID 48213
```

Вона працює, доки гра не завершиться, а її статус завершення повторює статус гри (див. [Коди завершення](#exit-codes)). Окремо крок встановлення horno вона не виконує: цю роботу робить сам старт гри.

## Прапори {#flags}

### Для окремих команд {#per-command}

| Прапор      | Короткий | Типово                                                    | Використовують               | Значення                                                                                                                                                                            |
| ----------- | -------- | --------------------------------------------------------- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--input`   | `-i`     | `opys.config.mjs`                                         | `build`, `install`, `launch` | Файл конфігурації для збирання. Відносний від поточного каталогу. Не дозволено з бандлом.                                                                                           |
| `--output`  | `-o`     | `output` конфігурації; коли немає жодного, друкувати JSON | `build`                      | Бандл для запису. Відносний шлях відносний від каталогу конфігурації.                                                                                                               |
| `--mode`    |          | ім’я команди: `build`, `install` або `launch`             | `build`, `install`, `launch` | Передається функції конфігурації як її `mode`. Ігнорується, коли дано бандл.                                                                                                        |
| `--feature` |          | немає                                                     | `install`, `launch`          | Ознаки рантайму для встановлення та запуску, одним списком через кому. Пробіли обрізаються, порожні записи відкидаються. Ознака вмикає значення з мітками правил, які її називають. |
| `--var`     |          | немає                                                     | `install`, `launch`          | `key=value`, щоб задати змінну маніфесту. Можна повторювати. Значенням є все після першого `=`, тому `--var token=` задає порожнє значення. Ключ не має бути порожнім.              |

`--feature` і `--var` стосуються як форми з конфігурацією, так і форми з бандлом. Значення `--var` накладаються поверх змінних, які маніфест уже має, тому власні типові значення бандла лишаються, доки ви їх не перекриєте.

Щоб задати кілька ознак, покладіть їх в один список через кому, наприклад `--feature java_console,other`. Повторення `--feature` зберігає лише останнє значення.

::: tip Консоль Windows
Ознака `--feature java_console` змушує змінну `java_bin` у Windows вказувати на `java.exe`, а не на `javaw.exe`.
:::

### Глобальні {#global}

Вони стосуються кожної команди. Їх можна ставити будь-де в командному рядку.

| Прапор                | Короткий | Типово | Значення                                                                                                                                                                                                                  |
| --------------------- | -------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--log-level <level>` |          | `info` | Скільки писати до stderr: `silent`, `error`, `warn`, `info` або `debug`. Невідомий рівень друкує попередження і використовує `info`.                                                                                      |
| `-v`                  |          |        | Те саме, що `--log-level debug`.                                                                                                                                                                                          |
| `--help`              | `-h`     |        | Друкує коротку довідку до stdout і завершується з кодом 0. Розпізнається лише в позиції команди, після глобальних прапорів: `opys build --help` є помилкою невідомого параметра. Запуск `opys` без команди теж її друкує. |

Прапора `--version` немає. Команда `opys --version` сприймається як невідома команда і завершується з кодом 1. Встановлена версія збігається з полем `version` файла `package.json` пакета `@opys/cli`, її також показує `npm ls -g @opys/cli`.

### Що змінює рівень журналу {#what-the-log-level-changes}

Параметр `--log-level` керує рядками, які opys пише через свій журналювальник: `Installing...`, `Ready in`, `Launching...`, `PID`, `Written to`, рядки кроку завантажувача і рядки збирання вигляду `[scope] message`, включно з попередженням про колізію змінних. Усі вони пишуться на рівні `info`, тому при `silent`, `error` або `warn` вони приховані.

Він не керує прогресом встановлення (див. нижче) і не керує помилками. Ті пишуться напряму і показуються завжди.

Параметр `-v` нічого видимого не змінює. Команда не пише рядків для налагодження, тому `debug` показує те саме, що й `info`.

## horno та install {#horno-and-install}

Деякі завантажувачі завершують встановлення на машині, яка їх запускає. Forge і NeoForge будують пропатчений клієнтський jar запуском процесорів, а найстаріші збирання Forge переписують клієнтський jar напряму. Рантайм не може зробити це під час встановлення, тому роботу виконує horno, невелика програма на Java, яка запускає гру. Що робить horno, описано в розділі [horno](/uk/internals/horno).

Команда `install` запускає horno один раз так, що запускати далі нічого:

1. Вона перевіряє, чи починається хоч один аргумент запуску в маніфесті з `-Dhorno.`. Якщо жоден, кроку завантажувача немає і `install` зупиняється.
2. Інакше вона будує запуск, описаний маніфестом, і додає `-Dhorno.installOnly=true` першим аргументом JVM.
3. Вона запускає цей процес і чекає, доки він завершиться.

Прапор додається лише в командному рядку. Він ніколи не записується в маніфест чи бандл, бо маніфест описує інсталяцію, а не окремий її запуск.

Якщо horno завершується з ненульовим кодом, `install` завершується з кодом 5. Повідомлення каже `The game exited with code N`, хоча насправді не вдався крок встановлення horno. Вивід вище нього належить самому horno, і читати треба його.

Команда `launch` не додає прапор і не виконує цей окремий крок. horno працює як частина старту гри.

## Вивід прогресу {#progress-output}

Прогрес пишеться до stderr. На терміналі він оновлюється на місці. У вивід, переданий далі каналом або захоплений, як у CI, загальний рядок потрапляє не частіше ніж раз на три секунди. Рядки окремих файлів і фаз усе одно пишуться в міру подій.

Типове встановлення друкує, по порядку:

- `Installing...`
- Загальну смугу, поки файли завантажуються, з відсотком, кількістю готових файлів і загальною кількістю, швидкістю та оцінкою часу, що лишився. Коли маніфест дає розміри файлів, відсоток міряється в байтах. Інакше він міряється у файлах.
- На терміналі, під загальною смугою, по одній смузі на файл, що саме завантажується, з його ім’ям і прогресом.
- `  ✓ <file>` коли кожне завантаження завершується, з ім’ям файла.
- ` Verifying...`, коли завантаження завершено.
- ` Extracting N archive(s)...`, коли є архіви для розпакування.
- ` Swept N stale file(s)`, коли видалено файли зі старішої інсталяції.
- ` Ready in <time>`, коли встановлення завершено.

Далі `install` друкує `Running the loader install...` і ` Installed`, якщо horno запускався. Команда `launch` друкує `Launching...` і ` PID <n>`.

Параметр `--log-level silent` ховає рядки `Installing...` і `Ready in`, але смуга і рядки окремих файлів і фаз усе одно пишуться.

## Коди завершення {#exit-codes}

| Код | Значення                                                                                                                                                                     |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 0   | Успіх. Гра або крок встановлення horno завершився з кодом 0.                                                                                                                 |
| 1   | Помилка використання, конфігурація чи бандл, який не читається або не імпортується, помилка рантайму, що не належить до кодів від 2 до 4, або неочікувана внутрішня помилка. |
| 2   | Помилка мережі під час встановлення. Не вдався мережевий запит.                                                                                                              |
| 3   | Не пройдено перевірку цілісності. Файли, що не збіглися з хешем, перелічено в stderr.                                                                                        |
| 4   | Не вдалося розпакувати. Архів і причина вказані в stderr.                                                                                                                    |
| 5   | Гра стартувала, а потім завершилася з помилкою, або не вдався крок встановлення horno.                                                                                       |

Код 1 покриває кілька різних несправностей. Повідомлення розрізняє їх:

- Помилки використання: невідомий прапор, `--var` без `key=value`, бандл разом із `--input`, другий шлях бандла або конфігурація без типового експорту. Повідомлення починається з `Error:`. Невідома команда повідомляється як `Unknown command '<name>'`, за яким іде текст використання.
- Помилки конфігурації, включно з відсутнім файлом конфігурації або таким, що кидає виняток, друкують `Unexpected error:` і далі стек викликів.
- Збій під час збирання, наприклад плагін, який не може досягти свого API, також друкує `Unexpected error:` і завершується з кодом 1. Коди від 2 до 4 описують лише встановлення.
- Бандл, який не читається, наприклад відсутній файл, теж друкує `Unexpected error:` і стек.
- Помилка рантайму, наприклад файл, який встановлення не змогло записати, друкує `Error:`.
- Неспроможність стартувати процес, наприклад неіснуючий бінарник Java, повідомляється через той самий шлях `Unexpected error:`.

Задайте `OPYS_QUIET=1`, щоб прибрати стек викликів з повідомлень `Unexpected error:`. Саме повідомлення все одно друкується.

::: warning Гра, убита сигналом, завершується з кодом 0
opys сприймає дочірній процес, що завершився без коду, а це трапляється, коли його вбиває сигнал, як успіх. Убита гра завершує opys з кодом 0, а не 5. Якщо запуск виглядає надто чистим, перевірте власний вивід гри.
:::
