# Акаунти, сервери, відеокарти

Ця сторінка для автора модпака, який хоче, щоб гравці входили через сервер під вашим керуванням, хоче бачити свій сервер у списку мережевої гри або хоче запускати гру на дискретній відеокарті. Для цього є чотири пакети: `authliberty` і `bifrost` для облікових записів, `serverlist` для списку серверів і `dgpuj` для відеокарти. Кожен розділ починається із завдання. Усі параметри описані на сторінці відповідного плагіна.

Ім’я гравця, UUID і токен є значеннями для машини запуску, тому вони належать до [`runClient`](/uk/guide/run-client): маніфест запікається в бандл, який отримає кожен гравець. `authliberty`, `serverlist` і `dgpuj` є плагінами. Вони працюють під час збирання, а бандл несе те, що вони підготували.

## Гра без облікового запису {#play-without-an-account}

`token: '0'` запускає гру без облікового запису Microsoft. Змінні `username`, `uuid` і `token` містять ім’я гравця, UUID і токен доступу. Ігрові плагіни передають їх далі як `auth_player_name`, `auth_uuid` і `auth_access_token` (а також `auth_session`, який теж приймає токен). opys не перевіряє токен і нічого ним не підписує, тому `'0'` тут є заглушкою. Її достатньо для одиночної гри та для серверів, що працюють в офлайн-режимі.

Задайте ці три значення у `runClient`:

```js
runClient: (manifest) => ({
  vars: {
    ...manifest.vars,
    root: userDataDir('my-pack'),
    username: 'Player',
    uuid: '00000000-0000-0000-0000-000000000001',
    token: '0',
  },
}),
```

`runClient` замінює кожне поле, яке повертає, тому додайте `manifest.vars` до `vars` через спред, інакше власні змінні плагінів будуть втрачені.

## Вхід гравців через власний сервер {#sign-players-in-against-your-own-server}

Тут працюють два компоненти, і вони виконують різні завдання. `authliberty` завантажує агент `-javaagent`, який спрямовує звернення гри до хостів Mojang на сервер, який ви назвете. Цей сервер говорить протоколом Yggdrasil, тим самим, на якому працює власна авторизація Mojang. `bifrost` випускає токен, який перевіряє сервер [Bifrost](https://gitlab.com/harmoniya/bifrost). Агент визначає, куди гра під’єднується, а токен визначає, хто такий гравець.

### Спрямування гри на свій сервер: authliberty {#point-the-game-at-your-server-authliberty}

`authliberty` є агентом у стилі authlib-injector. Він дає дві речі:

- **Один артефакт**: jar агента під шляхом `${library_directory}/net/harmoniya/authliberty/<version>/`, зафіксований за sha256, який повідомляє GitLab, коли такий є.
- **Одну групу запуску, `jvmArgs`**: `-javaagent:<path>`, а далі по одному `-Dminecraft.api.<server>.host=<url>` для кожного налаштованого хоста.

Хост, який ви не вказали, залишається на сервері Mojang.

| Ключ `hosts` | Системна властивість            | Типово у Mojang                     |
| ------------ | ------------------------------- | ----------------------------------- |
| `auth`       | `-Dminecraft.api.auth.host`     | `https://authserver.mojang.com`     |
| `account`    | `-Dminecraft.api.account.host`  | `https://account.mojang.com`        |
| `session`    | `-Dminecraft.api.session.host`  | `https://sessionserver.mojang.com`  |
| `services`   | `-Dminecraft.api.services.host` | `https://api.minecraftservices.com` |

`hosts` також може бути функцією. Її викликають один раз для кожного з цих чотирьох ключів, і вона повертає URL або `undefined`, щоб залишити цей хост на Mojang.

Версія є точною, наприклад `'0.3'`, або `'latest'`. Збірку `latest` замінюють щоразу, коли збирається гілка `main` проєкту AuthLiberty, а її хеш фіксується під час збирання, тому перезберіть модпак, щоб підхопити нову.

Додайте плагін до `plugins` і поставте його групу запуску першою в `args`, щоб перенаправлення вже діяло, перш ніж запуститься будь-який код авторизації:

```js
plugins: [
  minecraft('1.20.1'),
  authliberty('0.3', {
    hosts: {
      auth: 'https://auth.example.com',
      session: 'https://auth.example.com',
    },
  }),
  java('17'),
],
manifest: {
  command: ({ java }) => java.bin,
  args: ({ authliberty, minecraft }) => [
    authliberty.jvmArgs,
    minecraft.jvmArgs,
    minecraft.mainClass,
    minecraft.gameArgs,
  ],
  workdir: '${game_directory}',
},
```

`authliberty.jvmArgs` ставиться перед `minecraft.jvmArgs`. Параметри `project`, `gitlab` і `token` вказують, де опубліковано jar. Вони описані на [сторінці authliberty](/uk/plugins/authliberty).

### Випуск токена гравця: bifrost {#mint-the-player-s-token-bifrost}

`bifrost` є помічником, а не плагіном. Він не має фабрики і нічого не додає до маніфесту. Ви викликаєте `resolveBifrost` усередині `runClient`, один раз на запуск. Функція підписує JWT на Ed25519 (`alg: EdDSA`) з клеймами `uuid`, `username`, `iat` і `exp`, тобто такої форми, яку видає власна кінцева точка `/token` сервера Bifrost, тому сервер Bifrost приймає його за відповідним відкритим ключем. Типово токен живе добу.

`resolveBifrost` експортується з `@opys/bifrost`. `@opys/minecraft` реекспортує її як `resolveBifrost` і як `bifrost`. Функція приймає `privateKey` (ключ Ed25519 у форматі PKCS#8 PEM), `username` і `uuid`, а повертає `{ username, uuid, token }`, причому UUID записує без дефісів. Інші параметри перелічено на [сторінці bifrost](/uk/plugins/bifrost).

Прочитайте ключ зі змінних середовища і задайте ці три змінні у `runClient`:

```js
runClient: (manifest) => {
  const auth = resolveBifrost({
    privateKey: process.env.BIFROST_PRIVATE_KEY,
    username: 'Player',
    uuid: '00000000-0000-0000-0000-000000000001',
  });
  return {
    vars: {
      ...manifest.vars,
      username: auth.username,
      uuid: auth.uuid,
      token: auth.token,
    },
  };
},
```

Змінні `username`, `uuid` і `token` є тими самими трьома, що й для гри в офлайні, тому їх задають один раз, у тому самому місці, що й `token: '0'`.

::: warning Тримайте приватний ключ поза `manifest`
Маніфест записується в бандл, і його копію отримує кожен гравець, який його встановить. Ключ там стане ключем, який матимуть усі. `runClient` працює на машині запуску при кожному запуску, тому читайте ключ зі середовища там, як показано вище. Якщо `BIFROST_PRIVATE_KEY` не задано, `resolveBifrost` кине виняток і так і скаже.
:::

## Попереднє заповнення списку серверів {#pre-fill-the-server-list}

Плагін `serverlist` під час збирання записує файл `servers.dat` у каталог гри, тож гравець побачить ваші сервери в мережевій грі вже при першому запуску. Під час встановлення нічого не завантажується: файл генерується і їде в бандлі як блоб. Додайте його до `plugins`:

```js
plugins: [
  minecraft('1.20.1'),
  java('17'),
  serverlist([
    { name: 'My SMP', ip: 'mc.example.com' },
    { name: 'Test server', ip: 'test.example.com' },
  ]),
],
```

Кожен запис приймає три поля:

| Поле    | Обов’язкове | Значення                                            |
| ------- | ----------- | --------------------------------------------------- |
| `name`  | так         | Мітка, показана у списку.                           |
| `ip`    | так         | Адреса в тому вигляді, як її вводив би гравець.     |
| `rules` | ні          | Де застосовується запис. Відсутність означає всюди. |

Будь-яке інше поле є помилкою під час збирання, тому запис із `hidden` не збереться.

Файл потрапляє до `${game_directory}/servers.dat`. Параметр `path` записує його в інше місце. Докладніше на [сторінці serverlist](/uk/plugins/serverlist).

Записи з `rules` групуються за набором правил, а записи без правил утворюють власну окрему групу. Кожна група стає одним `servers.dat` з правилами цієї групи.

::: warning Виживає лише один набір правил
Файл кожної групи потрапляє за тим самим шляхом, а маніфест зберігає один артефакт на шлях, останній. Тому список, який має більше ніж одну групу, якщо рахувати записи без правил як групу, зберігає лише файл останньої групи. На машині, де правила цієї групи не виконуються, список взагалі не встановлюється. Використовуйте один набір правил для всіх ваших списків серверів.
:::

Файл фіксується за хешем, тому інсталятор повертає його назад щоразу, коли копія гравця відрізняється. Сервери, які гравець додає в грі, наступне встановлення замінює. Порожній список усе одно записує файл, тому `serverlist([])` очищає список.

## Використання дискретної відеокарти {#use-the-discrete-gpu}

На машині з вбудованою та дискретною відеокартами вибір робиться для кожного процесу окремо, для того процесу, який створює контекст OpenGL. Лаунчер, що запускає `javaw` як дочірній процес, не може змінити цей вибір для гри, бо гра є іншим процесом. Тому `dgpuj` має бути самою командою запуску. Він просить дискретну відеокарту у власному процесі, а потім запускає JVM усередині нього.

Дії відрізняються залежно від системи. У Windows лаунчер експортує символи, які шукають драйвери NVIDIA та AMD. У Linux він виставляє змінні PRIME render-offload від NVIDIA, і лише коли наявний пропрієтарний драйвер NVIDIA. У macOS примусово ввімкнути нічого не можна, тому він лише приймає JVM. Деталі є в [репозиторії dgpuj](https://github.com/harmoniya-net/dgpuj).

```js
plugins: [forge('1.20.1'), java('17'), dgpuj()],
manifest: {
  command: ({ dgpuj }) => dgpuj.bin,
  args: ({ dgpuj, forge }) => [
    dgpuj.home,
    forge.jvmArgs,
    forge.mainClass,
    forge.gameArgs,
  ],
  workdir: '${game_directory}',
},
```

`dgpuj.bin` є бінарником лаунчера. `dgpuj.home` розгортається в `--dgpuj-home ${java_home}` і каже лаунчеру, де шукати JVM. Він ставиться першим в `args`. Його можна не вказувати: плагін `java` експортує `JAVA_HOME` в середовище запуску, а лаунчер його читає. Залишайте `dgpuj.home`, лише якщо ви налаштували розташування JVM в інший спосіб і хочете його назвати.

Типово плагін надає такі платформи:

| ОС      | Архітектура | Архів     |
| ------- | ----------- | --------- |
| Windows | x86_64      | `.zip`    |
| Windows | aarch64     | `.zip`    |
| Linux   | x86_64      | `.tar.gz` |
| macOS   | x86_64      | `.tar.gz` |
| macOS   | aarch64     | `.tar.gz` |

Linux на aarch64 серед них немає. Кожен архів є окремим артефактом, обмеженим своєю ОС та архітектурою, тож гравець завантажує лише файл для своєї машини, і кожен зафіксовано за хешем sha256.

Параметр `version` вибирає `'latest'` (типово), `'prerelease'` або точний тег, наприклад `'v0.3.0'`. Плагін володіє змінною `dgpuj_dir`, типово це `${root}/dgpuj`, і змінною `dgpuj_bin`, яка вказує на бінарник для кожної ОС. Інші параметри описані на [сторінці dgpuj](/uk/plugins/dgpuj).
