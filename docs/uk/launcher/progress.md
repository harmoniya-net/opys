# Прогрес

Ця сторінка описує, що повідомляє `@opys/runtime` під час встановлення: фази, через які проходить встановлення, кожну подію, яку воно надсилає, і як перетворити ці події на смугу прогресу з оцінкою часу. Вона для розробника лаунчера, який уже викликав `install`, `prepare` або `launch` з розділу [Встановлення і запуск](./embedding).

Кожне встановлення це один колбек. Передайте `onProgress` у параметрах, і рантайм викликатиме його з об’єктом `InstallProgress` для кожного кроку. Немає емітера подій, до якого треба приєднуватися, і немає нічого, на що треба підписуватися окремо.

```js
import { install } from '@opys/runtime';

await install(
  { bundle: 'game.opys' },
  {
    vars: { root: '/srv/minecraft' },
    onProgress(p) {
      console.log(p.phase);
    },
  },
);
```

`prepare` і `launch` приймають той самий колбек усередині свого параметра `install`:

```js
import { launch } from '@opys/runtime';

const child = await launch(
  { bundle: 'game.opys' },
  {
    vars: { root: '/srv/minecraft' },
    install: { onProgress: (p) => console.log(p.phase) },
  },
);
```

`buildLaunch` і будь-який виклик з `install: false` нічого не встановлюють і нічого не надсилають.

## Фази {#phases}

Встановлення проходить шість фаз у такому порядку. П’ять із них звітують подіями. Фаза `scan` нічого не повідомляє, а про `fetch` повідомляють події `download`, а не подія з іменем `fetch`:

| Phase     | What happens                                                                                                         | Event                                  |
| --------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| `resolve` | Джерело відкривають або завантажують цілком, а його маніфест читають                                                 | `resolve`                              |
| `scan`    | Файли, що вже є на диску, гешують; наявні й такі, що збігаються, залишають                                           | none                                   |
| `fetch`   | Відсутні або неправильні файли завантажують або копіюють із бандла, якщо це блоби, починаючи з найбільших            | `download` and the `download:*` events |
| `verify`  | Кожен файл, отриманий під час цього запуску, гешують і звіряють із фіксованим значенням                              | `verify`                               |
| `extract` | Архіви з правилом розпакування розпаковують                                                                          | `extract`                              |
| `sweep`   | Файли, що відповідають шаблонам `restrict` з маніфеста, яких він не перелічує, і порожні каталоги під ними видаляють | `sweep`                                |

`scan` нічого не надсилає, тому на великій інсталяції, яка здебільшого вже є, після `resolve` виникає пауза, поки файли гешують. Чекайте цієї паузи перед першою подією `download`, а не зависання.

`verify` працює, лише коли перевірку цілісності увімкнено, а типово її увімкнено, якщо ви не передали `verifyIntegrity: false`. Вона перевіряє файли, які `fetch` щойно записав. Файл, який залишив `scan`, уже гешували. Подію `verify` надсилають, навіть якщо нічого не отримували. Фаза `extract` працює, лише коли маніфест має архів для розпакування, і вона розпаковує кожен такий архів під час кожного встановлення, незалежно від того, чи завантажували його цього разу. Подію `sweep` надсилають, лише коли щось видалили.

## Події {#events}

Кожна подія це об’єкт, поле `phase` якого її називає. Поля нижче це весь вміст кожної події. Читайте лише поля, перелічені для фази, яку обробляєте.

| `phase`          | Fields                                               | Emitted                                                                                        |
| ---------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `resolve`        | none                                                 | Один раз, першою, перед відкриттям джерела                                                     |
| `download`       | `fetched`, `total`, `skipped`, `bytes`, `totalBytes` | Один раз після `scan` зі значенням `fetched: 0`, потім один раз щоразу, коли файл завершується |
| `download:start` | `path`, `totalBytes`                                 | Коли завантаження файла починається                                                            |
| `download:bytes` | `path`, `bytes`                                      | У міру надходження даних файла                                                                 |
| `download:done`  | `path`                                               | Коли файл уже в кінцевому місці                                                                |
| `verify`         | none                                                 | Один раз, після завершення всіх завантажень                                                    |
| `extract`        | `count`                                              | Один раз, перед розпакуванням архівів; `count` це кількість                                    |
| `sweep`          | `removed`                                            | Один раз, якщо щось видалили; `removed` це кількість файлів і каталогів                        |

Типи живуть в `InstallProgress`, який експортує `@opys/runtime`.

У трьох подіях `download:*` поле `path` це шлях артефакта так, як його пише маніфест, тобто змінну на кшталт `${root}` не підставлено. Використовуйте його як ключ, щоб розрізняти файли. Щоб показати назву, візьміть її останній сегмент.

### `download` {#download}

Це подія, з якої будують смугу прогресу. Її поля означають:

- `fetched` і `total` рахують файли. `total` це файли, які треба завантажити під час цього запуску. Файл, що вже є і збігається з гешем, не входить до `total`. Його рахують у `skipped`.
- `bytes` це сума заявлених розмірів завершених файлів. Це не підрахунок байтів, прочитаних із мережі.
- `totalBytes` це сума заявлених розмірів файлів у `total`. Файл, якому маніфест не дає розміру, входить до кількості, але нічого сюди не додає, тому `totalBytes` менше на розмір таких файлів. Коли `totalBytes` дорівнює `0`, жоден файл цього запуску не має розміру, і доводиться повертатися до підрахунку файлів.

Подію `download` надсилають після `download:done` для того самого файла, тому коли ви бачите подію `download`, файл, який вона рахує, уже відзвітовано як готовий.

### `download:start` {#download-start}

Надсилають один раз на файл, коли рантайм починає його завантажувати. Поле `totalBytes` це розмір, який маніфест заявляє для цього файла, або `0`, коли маніфест не дає розміру. Подію не надсилають знову, якщо рантайм повторює файл після помилки.

### `download:bytes` {#download-bytes}

Надсилають у міру надходження даних. Поле `bytes` це кількість байтів цього файла, отриманих наразі в поточній спробі. Це не наскрізний підсумок за всіма файлами.

Про неї треба знати дві речі:

- Біндинг Node відкидає події `download:bytes`, щоб надсилати щонайбільше одну кожні 50 мс, за всіма файлами разом. Ви побачите менше таких подій, ніж отриманих чанків, і остання для файла може не надійти. Не покладайтеся на неї для підсумкового числа. Події `download:done` і наступна подія `download` це надійний запис.
- Файл, що зазнав помилки й повторюється, починається з нуля. Його `bytes` повертаються вниз. Зберігайте останнє значення для кожного шляху, а не додавайте їх.

Блоб, тобто файл, який везе бандл, копіюють, а не завантажують. Його подія `download:bytes`, коли її не відкидає ліміт вище, надходить один раз і несе повний розмір.

### `download:done` {#download-done}

Надсилають, коли файл готовий і вже в кінцевому місці. Приберіть файл з того, що показуєте як виконуване.

### `verify`, `extract`, `sweep` {#verify-extract-sweep}

Вони позначають пізніші фази. Подія `verify` не має полів. Подія `extract` каже, скільки архівів зараз розпаковуватимуть, і це саме те число, яке варто показати («Розпакування 3 архівів»). Подія `sweep` каже, скільки застарілих файлів і порожніх каталогів видалили.

## Смуга прогресу й оцінка часу {#a-progress-bar-and-an-eta}

Приклад нижче веде запис того, що завантажується, і обчислює частку виконаного встановлення та час, що лишився. Він рахує в байтах, коли маніфест дає розміри, і у файлах, коли не дає, і це той самий вибір, який робить CLI.

Створіть трекер до початку встановлення, щоб його годинник охоплював увесь запуск:

```js
import { install } from '@opys/runtime';

export function trackProgress() {
  const t0 = Date.now();
  let last = null; // остання подія `download`
  const inFlight = new Map(); // path -> { bytes, total } для файлів, що почалися

  function onProgress(p) {
    switch (p.phase) {
      case 'download':
        last = p;
        break;
      case 'download:start':
        inFlight.set(p.path, { bytes: 0, total: p.totalBytes });
        break;
      case 'download:bytes': {
        const f = inFlight.get(p.path);
        if (f) f.bytes = p.bytes;
        break;
      }
      case 'download:done':
        inFlight.delete(p.path);
        break;
    }
  }

  function snapshot() {
    if (last === null) return null;

    const sized = last.totalBytes > 0;
    // До байтів зараховують лише файли із заявленим розміром. Файл без розміру
    // не входить до `totalBytes`, тому додавання його байтів підняло б частку вище
    // того, що дозволяє знаменник.
    let flying = 0;
    for (const f of inFlight.values()) {
      if (f.total > 0) flying += f.bytes;
    }
    const done = sized
      ? Math.min(last.bytes + flying, last.totalBytes)
      : last.fetched;
    const all = sized ? last.totalBytes : last.total;

    const pct = all === 0 ? 1 : done / all;
    const seconds = (Date.now() - t0) / 1000;
    const rate = seconds > 0 ? done / seconds : 0; // байтів/с або файлів/с
    const etaSeconds = rate > 0 ? (all - done) / rate : null;

    return { pct, done, all, sized, etaSeconds };
  }

  return { onProgress, snapshot };
}
```

Потім передайте його колбек у встановлення й опитуйте знімок раз на секунду:

```js
const progress = trackProgress();

const timer = setInterval(() => {
  const s = progress.snapshot();
  if (s === null) return;
  const unit = s.sized ? 'bytes' : 'files';
  const eta =
    s.etaSeconds === null ? 'unknown' : `${Math.round(s.etaSeconds)} s`;
  process.stderr.write(
    `\r${(s.pct * 100).toFixed(1)}%  ${s.done}/${s.all} ${unit}  eta ${eta}   `,
  );
}, 1000);

try {
  await install(
    { bundle: 'game.opys' },
    { vars: { root: '/srv/minecraft' }, onProgress: progress.onProgress },
  );
} finally {
  clearInterval(timer);
}
process.stderr.write('\n');
```

Кілька зауважень про арифметику:

- Значення `done` це готові байти з `download` плюс байти файлів у польоті. Додавання байтів у польоті саме й рухає смугу під час великого файла, замість того щоб стояти, поки файл не завершиться.
- Швидкість міряють від початку запуску, тому вона включає час на визначення джерела й сканування. На початку швидкість нижча за саму швидкість завантаження.
- Файли, що вже є, не входять до `all`, тому відсоток це частка роботи, яку має виконати цей запуск. Рантайм не повідомляє розмірів пропущених файлів, тому частку всієї інсталяції можна отримати лише підрахунком: `(fetched + skipped) / (total + skipped)`.
- Оцінка часу це `(all - done) / rate`. Вона невідома, поки щось не завантажили.

## Як це робить CLI {#how-the-cli-does-it}

Команда `opys` малює таку саму смугу з тих самих подій, тобто в терміналі вона показує те, що обчислює приклад вище:

- Вона міряє в байтах, коли `totalBytes` більше за нуль, і у файлах інакше.
- Вона додає байти файлів у польоті до готового підсумку, обмеженого `totalBytes`. На відміну від приклада, вона додає кожен файл у польоті, зокрема й ті, що не мають заявленого розміру.
- Вона показує оцінку часу, лише поки `fetched < total`, і прибирає оцінку, коли лишилося менше секунди.
- Вона перемальовує щонайбільше кожні 80 мс. У терміналі перемальовує на місці, а коли вивід не термінал, пише один рядок кожні 3 секунди.

Вона малює один рядок на файл у польоті з подій `download:start`, `download:bytes` і `download:done`, пише рядок для кожної події `download:done`, рядок `Verifying...` для `verify`, `Extracting N archives...` для `extract` і `Swept N stale files` для `sweep`.

::: tip Тримайте колбек швидким
Колбек працює в потоці JavaScript, поки встановлення триває. Запишіть потрібне й поверніться. Перемальовуйте за таймером, як вище, а не на кожну подію. Подія `download:bytes`, зокрема, може надходити до двадцяти разів на секунду.
:::

Виконаний проміс це сигнал, що встановлення завершилося, а не остання подія: події доставляють асинхронно, і одна ще може надійти після нього.

## Коли встановлення не вдається {#when-an-install-fails}

Невдале встановлення відхиляє свій проміс, з помилкою `RuntimeError`, якщо аргумент не відхилили одразу, і події прогресу зупиняються в точці помилки. Що означає кожна помилка і що з нею робити, описано в розділі [Помилки](./errors).
