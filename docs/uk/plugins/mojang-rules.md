# @opys/mojang-rules

`@opys/mojang-rules` тримає типи формату правил Mojang: правило, яке щось дозволяє або забороняє для операційної системи чи ознаки. Користуйтеся ним, щоб називати типи правил у власному коді. Пакунок не має нативного коду і залежностей. Його єдиний код часу виконання це дві фабричні функції, наведені нижче. Обчислення живе в [`@opys/mojang`](/uk/plugins/mojang).

```sh
npm install @opys/mojang-rules
```

## Форма правила {#the-shape-of-a-rule}

Правило має дію і щонайбільше одне обмеження:

```ts
type RuleAction = 'allow' | 'disallow';

type MojangRule =
  | { action: RuleAction; os: OsConstraint }
  | { action: RuleAction; features: FeatureConstraint }
  | { action: RuleAction };

type MojangRuleset = MojangRule[];
```

У JSON від Mojang правило виглядає так:

```json
{ "action": "allow", "os": { "name": "linux" } }
{ "action": "disallow", "os": { "name": "osx", "arch": "aarch64" } }
{ "action": "allow", "features": { "is_demo_user": true } }
{ "action": "allow" }
```

Префікс `Mojang` має значення. Маніфест також може записати правило як рядок скороченого запису, такий як `'allow.os.linux'`. [`@opys/core`](/uk/plugins/core) приймає обидва написання, а його типи `Rule` і `Ruleset` допускають обидва. Типи тут це розгорнута форма, у яку розбирається кожне правило. Див. [Скорочений запис](#the-shorthand) нижче.

## Типи {#types}

```ts
type OsName = 'linux' | 'windows' | 'osx';

type OsArch = 'x86' | 'x86_64' | 'arm' | 'aarch64' | 'any';

interface OsOptions {
  name: string;
  version: string;
  arch: string;
}

interface OsConstraint {
  readonly name?: OsName;
  readonly version?: string;
  readonly arch?: OsArch;
}

type FeatureConstraint = Record<string, boolean>;
```

- `OsOptions` описує платформу, на якій обчислюється набір правил. `name` і `arch` з обмеження мусять дорівнювати `name` і `arch` платформи. Значення `any` не є символом підстановки: воно дорівнює лише платформі, чий `arch` це рядок `any`.
- `OsConstraint` задає будь-яке з трьох полів. Кожне задане поле мусить збігатися. Поле, яке не задано, ігнорується. `version` це регулярний вираз, який шукається у версії платформи будь-де в рядку, а не як цілий рядок. Шаблон записано в синтаксисі Rust `regex`, який не має перегляду вперед і назад та зворотних посилань. Обчислення кидає виняток на неправильному шаблоні, коли `name` і `arch` того самого обмеження вже збіглися.
- `FeatureConstraint` відображає назву кожної ознаки на `true` або `false`. Значення `true` означає, що ознака мусить бути увімкнена. `false` означає, що вона мусить бути вимкнена.

## Допоміжні функції {#helpers}

```ts
function emptyRuleset(): MojangRuleset;
function allowOsRuleset(name: OsName): MojangRuleset;
```

`emptyRuleset()` повертає `[]`. `allowOsRuleset('linux')` повертає `[{ action: 'allow', os: { name: 'linux' } }]`.

## Як обчислюється набір правил {#how-a-ruleset-is-evaluated}

Набір правил виконується, коли виконується кожне правило в ньому. Обчислювач не вибирає правило, як це робив би перший або останній збіг. Він перевіряє кожне правило по черзі і зупиняється на першому, яке не виконується. Порожній набір виконується.

Окреме правило виконується так:

| Правило                  | Коли виконується                                                        |
| ------------------------ | ----------------------------------------------------------------------- |
| `allow` без обмеження    | Завжди.                                                                 |
| `disallow` без обмеження | Ніколи.                                                                 |
| `allow` з `os`           | Обмеження `os` тримається на платформі.                                 |
| `disallow` з `os`        | Обмеження `os` не тримається.                                           |
| `allow` з `features`     | Кожна перелічена ознака увімкнена або вимкнена, як каже її значення.    |
| `disallow` з `features`  | Не кожна перелічена ознака увімкнена або вимкнена, як каже її значення. |

Обмеження `os` тримається, коли збігається кожне задане його поле. Обмеження `features` тримається, коли збігається кожна ознака в ньому.

Оскільки мусить триматися кожне правило, два правила `allow` не складаються в перевірку «або те, або те»:

```ts
// Не виконується на жодній платформі. На Linux провалюється правило windows, а на windows провалюється правило linux.
const bad: MojangRuleset = [
  { action: 'allow', os: { name: 'linux' } },
  { action: 'allow', os: { name: 'windows' } },
];

// Виконується всюди, крім osx.
const notOsx: MojangRuleset = [
  { action: 'allow' },
  { action: 'disallow', os: { name: 'osx' } },
];
```

Обчисліть набір правил функціями з [`@opys/mojang`](/uk/plugins/mojang):

```ts
import { satisfiesRuleset } from '@opys/mojang';

satisfiesRuleset(notOsx, { name: 'linux', version: '6.12', arch: 'x86_64' }); // true
```

## Читання правила {#reading-a-rule}

Правило, прочитане з JSON, вважається правилом `os`, якщо воно підходить до тієї форми, потім правилом `features`, потім голим `allow` або `disallow`. Ключі, яких воно не знає, ігноруються.

::: warning Два обмеження або таке, що не читається
Правило, яке дає і `os`, і `features`, зберігає лише `os`. Правило, чий `os` не читається, таке як `{ "name": "solaris" }` або невідомий `arch`, читається як голе правило без обмеження: `allow` тоді тримається на кожній платформі, а `disallow` на жодній. Жоден із випадків не повідомляється як помилка.
:::

## Скорочений запис {#the-shorthand}

Маніфест може записати правило як рядок. Рядок це шлях, розділений крапками: дія, потім те, чого стосується правило, потім значення.

| Скорочений запис                | Розгорнута форма                                               |
| ------------------------------- | -------------------------------------------------------------- |
| `'allow'`                       | `{ action: 'allow' }`                                          |
| `'disallow'`                    | `{ action: 'disallow' }`                                       |
| `'allow.os.osx'`                | `{ action: 'allow', os: { name: 'osx' } }`                     |
| `'allow.os.linux@10\\.'`        | `{ action: 'allow', os: { name: 'linux', version: '10\\.' } }` |
| `'allow.arch.x86_64'`           | `{ action: 'allow', os: { arch: 'x86_64' } }`                  |
| `'allow.features.is_demo_user'` | `{ action: 'allow', features: { is_demo_user: true } }`        |

У скороченому записі ознака завжди називає `true`. Щоб вимагати вимкнену ознаку, користуйтеся `disallow`: `'disallow.features.is_demo_user'` виконується, коли ознака відсутня. Текст після `@` у правилі `os` це шаблон `version`. Скорочений запис не може задати одночасно назву ОС і архітектуру.

Скорочений запис належить `@opys/core`. Два пакунки, які обчислюють правила, різняться тим, що приймають:

| Пакунок                              | Чи приймає скорочений запис                                                       |
| ------------------------------------ | --------------------------------------------------------------------------------- |
| [`@opys/core`](/uk/plugins/core)     | Так. Його `Ruleset` приймає рядок, розгорнуте правило або масив будь-якого з них. |
| [`@opys/mojang`](/uk/plugins/mojang) | Ні. `decodeRuleset('allow.os.linux')` кидає виняток.                              |

Правила маніфеста описано в [довідці маніфеста](/uk/reference/manifest).
