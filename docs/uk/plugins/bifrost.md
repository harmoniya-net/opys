# bifrost

`bifrost` підписує токен входу для одного гравця, локально, під час запуску. Використовуйте його, коли ваші гравці входять на власний сервер, який перевіряє токени Bifrost, а ви тримаєте приватний ключ Ed25519, що відповідає відкритому ключу сервера. Токен оминає OAuth-потік `/token` самого Bifrost: ви випускаєте його самі, на машині запуску, щоразу, коли гра стартує.

`bifrost` це не плагін. Це функція, яку ви викликаєте всередині `runClient`, що виконується на машині запуску при кожному запуску. Вона повертає ім’я користувача, UUID і токен, а ви кладете їх у `vars`.

## Сигнатура {#signature}

```ts
resolveBifrost(options: BifrostOptions): BifrostAuth
```

Вона експортується з `@opys/bifrost` під назвою `resolveBifrost`, а з `@opys/minecraft` під обома назвами, `resolveBifrost` і коротшою `bifrost`. Обидві вказують на ту саму функцію.

## Параметри {#options}

| Назва        | Тип                 | Типово              | Значення                                                                                                     |
| ------------ | ------------------- | ------------------- | ------------------------------------------------------------------------------------------------------------ |
| `privateKey` | `string`            | немає, обов’язковий | Приватний ключ Ed25519, PEM, PKCS#8. Докладніше нижче.                                                       |
| `username`   | `string`            | немає, обов’язковий | Ім’я гравця. Потрапляє в токен як клейм `username`.                                                          |
| `uuid`       | `string`            | немає, обов’язковий | UUID гравця. Перед підписом дефіси прибираються, а решта літер стає малою. Інакше значення не перевіряється. |
| `expiresIn`  | `number`            | `86400` (24 години) | Час життя токена в секундах. Значення `0` прибирає клейм `exp`, тож токен ніколи не спливає.                 |
| `now`        | `number` або `Date` | поточний час        | Момент випуску, у мілісекундах від початку епохи. Потрібен рідко: він робить токен відтворюваним у тесті.    |

Невідомий параметр це помилка, тож неправильно написане ім’я параметра завалить запуск, а не буде тихо проігнороване.

### `privateKey` {#privatekey}

Ключ це PEM у форматі PKCS#8, такий, як записує `openssl` для ключа Ed25519. Приймаються дві форми, щоб ключ можна було тримати і в однорядковому налаштуванні на зразок файлу `.env`:

- увесь PEM зі справжніми розривами рядків;
- один рядок, де кожен розрив рядка записано двома символами `\n`, з рядками `-----BEGIN PRIVATE KEY-----` або без них.

Ключ іншого алгоритму, наприклад RSA, відхиляється з повідомленням, що ключ має бути Ed25519. Порожній або відсутній ключ відхиляється з повідомленням, яке називає `BIFROST_PRIVATE_KEY`.

## Що повертає функція {#what-it-returns}

```ts
interface BifrostAuth {
  username: string; // як передано
  uuid: string; // як передано, але без дефісів і малими літерами
  token: string; // підписаний JWT, alg EdDSA
}
```

Клейми токена це `uuid`, `username`, `iat` (у секундах) і, якщо `expiresIn` не дорівнює `0`, `exp`. Форма в нього така сама, як у токена, який видає власна кінцева точка `/token` проекту Bifrost, тому сервер, що перевіряє токени Bifrost, приймає його за відповідним відкритим ключем.

Підпис детермінований: ті самі параметри з тим самим `now` дають той самий токен. Без `now` два токени розійдуться, щойно годинник дійде до наступної секунди.

## Як покласти це у `vars` {#putting-it-into-vars}

Ванільна гра читає три змінні запуску: `username`, `uuid` і `token`. Її власні змінні, такі як `auth_player_name` і `auth_access_token`, визначаються з цих трьох. Тому поверніть їх під цими назвами, а решту `manifest.vars` розгорніть без змін:

```js
runClient: (manifest) => {
  const auth = resolveBifrost({ /* … */ });
  return {
    vars: {
      ...manifest.vars,
      username: auth.username,
      uuid: auth.uuid,
      token: auth.token,
    },
  };
},
```

`runClient` замінює `vars` цілком, тож саме розгортання зберігає `root` та інші змінні маніфесту.

::: warning Приватний ключ залишається на машині запуску
Ніколи не кладіть `privateKey` чи токен у `manifest`. Усе, що є в `manifest`, запікається в бандл і роздається кожному гравцю, а ключ у бандлі це ключ, яким токени може випускати будь-хто. Ключу місце лише в `runClient`: ця функція виконується на машині, що запускає гру, а її результат ніколи не записується в бандл.

Читайте ключ зі середовища, як у прикладі, а не записуйте його у файл конфігурації.
:::

## Приклад {#example}

Конфігурація збирається без вашого ключа, бо `runClient` виконується лише під час запуску. Ключ читається зі середовища, коли гра стартує.

<<< @/examples/plugin-extras-bifrost/opys.config.mjs

Запустіть її з ключем у середовищі:

```sh
export BIFROST_PRIVATE_KEY="$(cat path/to/key.pem)"
opys launch
```

Збирання конфігурації і зазирання всередину `game.opys` показує, що там немає ні ключа, ні токена: бандл тримає `${username}`, `${uuid}` і `${token}` як змінні, якими вони є, а значення надходять уже під час запуску.

Токен спливає за 24 години, якщо ви не встановили `expiresIn`. Оскільки `runClient` виконується при кожному запуску, кожен запуск отримує свіжий токен.
