# @opys/dev

`@opys/dev` це SDK для збирання. Ним ви пишете конфігурацію або плагін, що її живить: тут помічники для конфігурації, рушій збирання, контракт плагіна і два помічники, до яких тягнеться плагін, `files` і `userDataDir`. Покроковий приклад плагіна див. у [Написанні плагіна](/uk/reference/writing-a-plugin).

```sh
npm install -D @opys/dev
```

Експорти згруповано за призначенням. Типи, які називає сигнатура, перелічено в тій самій групі.

## Конфігурація {#config}

| Експорт         | Сигнатура                                                                 | Що робить                                                               |
| --------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| `defineConfig`  | `(input: OpysConfigInput) => OpysConfigInput`                             | Тотожний помічник для типового експорту `opys.config.mjs`.              |
| `resolveConfig` | `(input: OpysConfigInput, ctx: OpysConfigContext) => Promise<OpysConfig>` | Викликає функційну форму з `ctx` або повертає конфігурацію-об’єкт як є. |

`@opys/dev` не завантажує файл. CLI імпортує `opys.config.mjs`, а потім викликає `resolveConfig`. Кожне поле конфігурації описано у [Файлі конфігурації](/uk/guide/config).

| Тип                  | Форма                                                                                                                                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OpysConfig`         | `{ plugins, manifest, output?, runClient? }`                                                                                                                                                                                                   |
| `OpysManifestConfig` | Блок `manifest`: `command` і `args`, а також необов’язкові `workdir`, `envs`, `vars`, `artifacts`, `restrict`. Значення `command` і `args` це функції від `PluginMap`. Значення `workdir` і `envs` це або звичайні значення, або такі функції. |
| `OpysConfigInput`    | `OpysConfig` або функція з `OpysConfigContext` в нього (може повертати проміс)                                                                                                                                                                 |
| `OpysConfigContext`  | `{ mode: string }`. Значення `--mode` або назва команди (`build`, `install` чи `launch`), коли прапорця не передано                                                                                                                            |
| `PluginMap`          | `Record<string, LaunchGroups>`, за іменем плагіна                                                                                                                                                                                              |
| `ArgItem`            | `Valset \| Val \| string`, один елемент зібраних `args`                                                                                                                                                                                        |

## Рушій {#engine}

| Експорт         | Сигнатура                                                   | Що робить                                                               |
| --------------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| `buildManifest` | `(config: OpysConfig, ctx: BuildContext) => Promise<Built>` | Запускає `build` кожного плагіна, а потім зливає результати в маніфест. |

`Built` це `{ manifest: Manifest; blobs: Blobs }`. Ці двоє подорожують разом: `writeBundle` з `@opys/core` публікує їх одним файлом, а `@opys/runtime` встановлює гру прямо з них.

`buildManifest` запускає плагіни паралельно. Потім він викликає акцесори `command`, `args`, `workdir` і `envs` з блоку `manifest`, передаючи групи запуску кожного плагіна. Групи використовуються лише там і не входять до результату. Саме злиття виконано в нативному коді. Його попередження, наприклад про одну змінну, встановлену двома плагінами, передаються в `ctx.log` з областю `opys`.

## Контракт плагіна {#the-plugin-contract}

| Експорт        | Сигнатура                                 | Що робить                                                                                                                      |
| -------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `definePlugin` | `(plugin: OpysPlugin) => ChainablePlugin` | Повертає новий плагін з тими самими `name` і `build` та ланцюжковими методами нижче. Інші властивості об’єкта не переносяться. |

Плагін це об’єкт із `name` і хуком `build`. Конструювання не робить вводу-виводу: конструктор повертає об’єкт, а вся робота з мережею і диском відбувається в `build`.

```ts
interface OpysPlugin {
  name: string;
  build(ctx: BuildContext): Promise<Contribution> | Contribution;
}

interface BuildContext {
  log(scope: string, message: string): void; // CLI друкує "[scope] message"
  configDir: string; // абсолютний каталог файла opys.config.mjs
  mode: string; // значення --mode або назва команди
}

interface Contribution {
  artifacts?: Artifact[];
  blobs?: Blobs; // де лежать блоб-артефакти цього плагіна
  vars?: ValDefs;
  launch?: LaunchGroups; // іменовані фрагменти для акцесорів конфігурації
  envs?: ValDefs; // середовище запуску; останній плагін перемагає, конфігурація важливіша
}

type LaunchGroups = Record<string, Valset | Val | string>;
```

`envs` зливається між плагінами в порядку списку. Колізія дає попередження, а `manifest.envs` у конфігурації це останній шар.

### Ланцюжкові методи {#fluent-methods}

`ChainablePlugin` це `OpysPlugin` із п’ятьма додатковими методами. Кожен повертає новий плагін з іще одним перетворенням його артефактів, тож оригінал не змінюється, а ланцюжок читається зліва направо. Перетворення змінюють лише `artifacts`. Значення `vars`, `launch`, `blobs` і `envs` проходять крізь них.

| Метод             | Сигнатура                                                    | Що робить                                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `exclude`         | `(match: Selector) => ChainablePlugin`                       | Відкидає кожен артефакт, що збігається.                                                                                                                                                 |
| `addRule`         | `(match: Selector, rules: RulesetInput) => ChainablePlugin`  | Додає набір правил до `rules` кожного артефакту, що збігається. Набір правил виконується, лише коли виконується кожне правило в ньому, тож артефакт потім діє у меншій кількості місць. |
| `removeIntegrity` | `(match: Selector) => ChainablePlugin`                       | Очищає `integrity` в артефактах, що збігаються, тож вони встановлюються без перевірки.                                                                                                  |
| `updateFirst`     | `(match: Selector, patch: ArtifactPatch) => ChainablePlugin` | Неглибоко зливає патч у перший артефакт, що збігається.                                                                                                                                 |
| `updateMany`      | `(match: Selector, patch: ArtifactPatch) => ChainablePlugin` | Неглибоко зливає патч у кожен артефакт, що збігається.                                                                                                                                  |

`ArtifactPatch` це `Partial<Artifact>` або функція з артефакту в нього. `RulesetInput` це все, що приймає `parseShortRuleset`: `Ruleset` в обох написаннях. Див. [написання правил](/uk/plugins/core#rules).

```js
const extra = files({ from: 'extra', to: 'mods/${rel}' })
  .exclude((a) => a.path.endsWith('.tmp'))
  .addRule((a) => a.path.endsWith('.jar'), 'allow.os.linux');
```

## Селектори {#selectors}

| Експорт           | Сигнатура                                                 | Що робить                                      |
| ----------------- | --------------------------------------------------------- | ---------------------------------------------- |
| `Selector`        | `string \| string[] \| ((artifact: Artifact) => boolean)` | Каже, до яких артефактів застосовується метод. |
| `matchesSelector` | `(selector: Selector, artifact: Artifact) => boolean`     | Перевіряє один артефакт проти селектора.       |

Рядок або масив рядків це glob-шаблон або їхній список, які зіставляються зі шляхом `artifact.path`. Масив збігається, коли збігається будь-який його шаблон. Функція це предикат, який отримує цілий артефакт. Синтаксис glob-шаблонів описано під [Glob-шаблонами](/uk/plugins/core#globs) в `@opys/core`.

::: warning Зіставляйте шлях у тому вигляді, як записано
Шлях, який бачить селектор, це той, що записав плагін, з нерозгорнутими посиланнями на кшталт `${root}`. У glob-шаблоні `{` і `}` означають чергування, тому шаблон на зразок `${root}/mods/*.jar` не збігається з текстом `${root}`. Починайте шаблон із `**/` або використовуйте предикат.
:::

## Файли {#files}

| Експорт | Сигнатура                                    | Що робить                                        |
| ------- | -------------------------------------------- | ------------------------------------------------ |
| `files` | `(options: FilesOptions) => ChainablePlugin` | Кожен файл під локальним каталогом як артефакти. |

| Параметр | Тип                  | Значення                                                                                |
| -------- | -------------------- | --------------------------------------------------------------------------------------- |
| `from`   | `string`             | Каталог для читання відносно файла конфігурації.                                        |
| `to`     | `FileTemplate`       | Шлях встановлення. Типово це `rel` файла.                                               |
| `url`    | `FileTemplate`       | Де публікується кожен файл. Його наявність і робить файли вказаними замість вбудованих. |
| `hash`   | `'sha1' \| 'sha256'` | Хеш, яким фіксується кожен файл. Типово `sha1`. Дозволено лише з `url`.                 |

`FileTemplate` це рядок або функція. Рядок може використовувати `${rel}`, `${dir}` і `${filename}`. Будь-яке інше `${var}` залишається для встановлення. Функція отримує `LocalFile` з полями `rel`, `dir`, `filename`, `abs` і `size`. Лише форма з функцією бачить `abs`, шлях на машині збирання.

```js
files({ from: 'server-files', to: '${root}/${rel}' }); // везеться в бандлі
files({ from: 'mods', to: 'mods/${rel}', url: 'https://cdn.example/${rel}' });
```

Береться кожен звичайний файл під `from`, включно з підкаталогами, у порядку шляхів. Символічне посилання пропускається. Без `url` кожен файл стає блобом, названим своїм sha256, і подорожує в бандлі. З `url` кожен файл це артефакт, що вказує на опубліковану вами копію, зафіксовану своїм `hash` і розміром. Типи це `FilesOptions`, тобто `EmbeddedFiles` або `PublishedFiles`, а також `FileTemplate`. Сторінка плагіна це [files](/uk/plugins/files).

## Шляхи {#paths}

| Експорт       | Сигнатура                  | Що робить                                                |
| ------------- | -------------------------- | -------------------------------------------------------- |
| `userDataDir` | `(name: string) => string` | Каталог даних користувача для `name` за домовленістю ОС. |

У Windows це `%APPDATA%\<name>` або `<name>` у домашньому каталозі, коли `APPDATA` не встановлено. У macOS це `~/Library/Application Support/<name>`. В інших системах це `$XDG_DATA_HOME/<name>` або `~/.local/share/<name>`, коли це не встановлено.

::: warning
`userDataDir` визначає каталог машини, на якій виконується. Використовуйте його в `runClient`, що виконується при кожному запуску. У `manifest.vars` він би запік шлях машини збирання в кожен бандл. Див. [Значення під час запуску](/uk/guide/run-client).
:::

## Помічники для завантажувачів {#loader-helpers}

Вони призначені для плагіна, що обгортає документ версії, такого як завантажувач.

| Експорт        | Сигнатура                             | Що робить                                                                           |
| -------------- | ------------------------------------- | ----------------------------------------------------------------------------------- |
| `launchGroups` | `(t: LoaderTemplate) => LaunchGroups` | Проєктує поверхню запуску шаблона в `command`, `jvmArgs`, `mainClass` і `gameArgs`. |

`LoaderTemplate` це `{ launch: Launch; jvmArgs: Valset; mainClass: Val; gameArgs: Valset }`.
