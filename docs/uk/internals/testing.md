# Тестування

Ця сторінка перелічує перевірки у репозиторії, від найдешевшої до найдорожчої, з командою для кожної і тим, що вона доводить. Вона для учасника, який вирішує, що запустити перед комітом, і для кожного, хто хоче знати, що покриває CI, а чого не покриває.

## Шари {#the-layers}

| Шар                                | Команда                                  | Що доводить                                                                                        | Виконується у CI                              |
| ---------------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| Перевірка архітектури              | `npm run architecture`                   | Правила залежностей і стіни тримаються                                                             | Так                                           |
| Власні тести перевірки архітектури | `npm run test:architecture`              | Перевірка архітектури може впасти                                                                  | Так                                           |
| Модульні тести Rust                | `cargo test --workspace`                 | Поведінка крейтів, включно з резолверами проти loopback-серверів                                   | Так (також `opys-runtime` на Windows)         |
| Модульні тести JS                  | `npm test`                               | Те, що додають обгортки TypeScript                                                                 | Так                                           |
| Перевірка типів                    | `npm run typecheck`                      | Типи, включно з кодом тестів                                                                       | Так                                           |
| Димовий тест napi                  | `node scripts/smoke-napi.mjs`            | Кожен біндинг завантажується і один раз переходить у Rust                                          | Ні                                            |
| Жива інтеграція                    | `npm run test:int`                       | Справжні API Mojang, Forge, Modrinth, CurseForge і постачальників Java відповідають як очікувалося | Ні                                            |
| Приклади з документації            | `cd docs && npm run examples`            | Кожна конфігурація, показана у документації, збирається                                            | Лише після пушу в `main`, який змінює `docs/` |
| Матриця запусків                   | `node run.mjs` у `scripts/launch-matrix` | Зібраний маніфест встановлюється, запускається і показує вікно гри                                 | Ні (лише вручну)                              |

Запускайте перші шари перед кожним комітом. Пізніші потребують мережі, дисплея або багато часу, і їх запускають, коли зміна торкається того, що вони стережуть. Хук pre-commit форматує staged TypeScript, JavaScript і Markdown засобом prettier, запускає перевірку архітектури і, коли staged є файл `.rs`, запускає `cargo clippy`. Він не запускає `cargo fmt`, який перевіряє CI.

Зберіть пакети один раз перед усім, що їх завантажує. `npm run build` у корені репозиторію збирає кожен пакет TypeScript і кожен біндинг napi. Збирання біндингу записує файл `.node` і `index.js` у його каталог `crates/*-napi`, який димовий тест завантажує напряму.

## Перевірка архітектури {#architecture-check}

```sh
npm run architecture        # node scripts/check-architecture.mjs
npm run test:architecture   # node --test scripts/architecture/checks.test.mjs scripts/release/order.test.mjs
```

`npm run architecture` тримає дерево у межах, записаних як дані у `scripts/architecture/rules.mjs`. Він читає лише маніфести і джерела, тому йому нічого зібраного не потрібно. Він перевіряє граф залежностей між крейтами і пакетами, стіни, які тримають бік збирання окремо від рантайму, один біндинг napi на крейт, і те, що кожен імпорт оголошено у `package.json`. Він також перевіряє два списки, які досі ведуться вручну, кореневий `workspaces` і димовий тест, а також те, що workflow релізу досі виводить решту. Правила є списками дозволеного: крейт або пакет, якого файл не називає, провалює перевірку, тож навмисна зміна архітектури означає правку `rules.mjs`. [Архітектура](/uk/internals/architecture) описує, що він тримає.

`npm run test:architecture` запускає тести самої перевірки і коду порядку публікації на crates.io у `scripts/release/order.mjs`. Кожен тест архітектури вручну будує невеликий справний світ і ламає його по одному правилу, щоб показати, що кожне правило може впасти. Перевірка, яка не може впасти, нічого не перевіряє, тож змінюйте перевірку і цей набір разом.

## Модульні тести Rust {#rust-unit-tests}

```sh
cargo test --workspace
```

Кожен крейт тестує власну поведінку у своїх модулях `src` і у `tests/`. Резолвер розділено на чисту частину і один мережевий виклик, тож більшість того, що він робить, тестується на простих вхідних даних. Мережевий виклик тестується проти loopback-сервера, а не мока. Зразок лежить у `crates/opys-java/tests/common/mod.rs`: він прив’язує слухача до `127.0.0.1` на ефемерному порту і спрямовує `apiBase` резолвера на нього. Інші крейти резолверів мають той самий помічник.

Поведінка, перенесена з одного крейту в інший, тестується там, де вона тепер живе, а не двічі: тести JavaScript пакета `@opys/java` покривають лише замикання плагіна і типізовану поверхню, а резолвери тестуються у `crates/opys-java/tests`.

`opys-forge`, `opys-neoforge`, `opys-cleanroom` і `opys-lwjgl3ify` мають по одному тесту, який типово пропускається: `tests/documents.rs` розбирає кожен опублікований документ цієї родини. Вкажіть змінною `OPYS_FORGE_DOCUMENTS` (або `OPYS_NEOFORGE_DOCUMENTS`, `OPYS_CLEANROOM_DOCUMENTS`, `OPYS_LWJGL3IFY_DOCUMENTS`) на локальну копію дерева `versions/` сайту і запустіть `cargo test -p opys-forge --test documents -- --ignored`. Перезапускайте його щоразу, коли змінюється вихід генератора або `VersionPatch`.

## Модульні тести JS і перевірка типів {#js-unit-tests-and-typecheck}

```sh
npm test
npm run typecheck
```

`npm test` запускає `vitest run tests/unit` у кожній робочій області, яка визначає скрипт `test`. Набори покривають лише те, що пакет TypeScript додає поверх свого крейту: замикання плагінів, завантажувач конфігурації, типізовану поверхню. Логіка, яка живе у Rust, тестується у Rust. Постійна планка покриття становить близько 99% рядків. Жоден скрипт у `package.json` її не вимагає, а `@vitest/coverage-v8` встановлено для її вимірювання.

`npm run typecheck` запускає `tsc --noEmit -p tsconfig.json` у кожному пакеті. Кожен `tsconfig.json` включає і `tests/**/*.ts`, і `lib/`, крім того, що у `@opys/mojang-rules`, який містить лише типи і не має тестів. Помилка типу у тесті провалює ту саму команду, що й помилка у бібліотеці.

## Димовий тест napi {#napi-smoke-test}

```sh
node scripts/smoke-napi.mjs
```

Запускайте його після `npm run build`. Скрипт завантажує `index.js` кожного біндингу напряму з його каталогу `crates/*-napi` і викликає його: декодування і кодування core, парсери Mojang, злиття рушія dev, резолвер кожного крейту плагінів і встановлення невеликого бандла рантаймом у тимчасовий каталог. Там, де виклик виходив би у мережу, скрипт замість сервісу піднімає loopback-сервер: Adoptium, кінцеві точки Mojang, індекси Fabric, Forge, NeoForge, Cleanroom і lwjgl3ify, GitLab, Modrinth, CurseForge і API релізів GitHub.

Він друкує `result: N passed, M failed` і завершується з кодом 1, якщо впала хоч одна перевірка.

## Жива інтеграція {#live-integration}

```sh
CURSEFORGE_TOKEN=... npm run test:int
```

Це запускає `vitest run tests/integration` у кожній робочій області, яка визначає скрипт `test:int`: `@opys/cli`, `@opys/mojang`, `@opys/java` і `@opys/minecraft`. Набори звертаються до справжніх сервісів Mojang, Forge, Modrinth, CurseForge, Adoptium, Azul і GitHub, тому їм потрібен доступ до мережі.

Тести CurseForge потребують ключа API у змінній середовища `CURSEFORGE_TOKEN`. У `packages/minecraft/tests/integration/plugins.test.ts` ці блоки пропускаються, коли змінна не задана, а решта набору далі виконується. Перевірка прикладів з документації теж читає цю змінну.

CI ніколи не запускає ці тести. Вони залежать від сервісів поза репозиторієм, тож провал напевно нічого не каже про код.

## Приклади з документації {#docs-examples}

```sh
cd docs && npm run examples
```

Це запускає `docs/check-examples.mjs`, який збирає кожну конфігурацію `docs/examples/<name>/opys.config.mjs` зібраним CLI. Сторінка включає приклад за посиланням, тож сторінка не може показати конфігурацію, яка не збирається. Скрипту потрібні зібрані пакети (`npm run build` у корені) і доступ до мережі, бо збирання визначає справжні версії. Приклад, чиє ім’я містить `curseforge`, пропускається з повідомленням, коли `CURSEFORGE_TOKEN` не задано.

Джоба `examples` у `.github/workflows/docs.yml` запускає той самий скрипт. Цей workflow виконується після пушу в `main`, який змінює `docs/**` або сам файл workflow, і після ручного запуску. Джоба не блокує деплой сайту: червона клітинка означає, що приклад більше не визначається, а не те, що сайт зламано.

## Матриця запусків {#the-launch-matrix}

Матриця є єдиною перевіркою того, що маніфест виконується. Усе вище зупиняється на маніфесті, який визначається. Для кожного кейса вона збирає бандл, встановлює його, запускає гру холодно, потім запускає ще раз тепло, і зараховує кейс, коли обидва запуски показують вікно гри і гра далі працює.

Вона виконується вручну, локально або через workflow з `workflow_dispatch`, і ніколи після пушу або за розкладом. Кейс завантажує до гігабайта, а те, що вона стереже (опубліковані документи версій і horno), змінюється без коміту сюди. Запускайте її після релізу horno або після зміни у крейті завантажувача, у рантаймі чи у horno. Червоний прогін з однаковою ймовірністю є зміною у першоджерелі або багом тут, тому читайте скриншот і лог, перш ніж звинувачувати код.

### Списки кейсів {#the-case-lists}

`scripts/launch-matrix/gen-cases.mjs` записує три списки з живих індексів Forge і NeoForge і з метасервісу Fabric. Списки ігноруються гітом, тому запускайте генератор перед `run.mjs`. Workflow робить це на кожному прогоні.

| Файл               | Кейси | Вміст                                                                                                                                                                                                                                             |
| ------------------ | ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `cases.slice.json` | 12    | Те, що workflow запускає типово: Forge 1.7.10, 1.12.2, 1.16.5, 1.20.1 і 1.21.1, найновіший Forge, Forge 1.20.2 і 26.1 (дві збірки, які ламаються першими на новій Java), NeoForge 1.21.1, найновіший NeoForge, а також найновіші Fabric і ваніль. |
| `cases.json`       | 39    | Ключовий набір: розкид версій Minecraft за завантажувачами, Cleanroom і lwjgl3ify, а також три ванільні кейси на інших постачальниках (Zulu і GraalVM).                                                                                           |
| `cases.full.json`  | 134   | Ключовий набір плюс кожна версія Minecraft, яку публікують індекси Forge і NeoForge.                                                                                                                                                              |

Кількості взяті з останнього запуску генератора і змінюються разом з індексами. Генератор підбирає Java для кейса за версією і фіксує дві збірки Forge на Java, на якій вони можуть стартувати: Forge 1.7.2 на Java 7 (Zulu) і Forge 1.16.4 на `8u312-b07`. Ідентифікатор кейса має форму `<loader>-<version>-j<java>`, з доданим `-<vendor>`, коли задано постачальника, наприклад `forge-1.16.5-j8`.

### Запуск {#running-it}

```sh
npm run build                         # матриця керує packages/cli/dist
cd scripts/launch-matrix
node gen-cases.mjs                    # записує три списки
node run.mjs                          # cases.json, ключовий набір
node run.mjs --cases cases.full.json  # кожна версія, яку публікують Forge і NeoForge
node run.mjs --cases cases.slice.json --only forge-1.20.1
```

`run.mjs` приймає такі прапорці:

| Прапорець            | Типово        | Дія                                                                                     |
| -------------------- | ------------- | --------------------------------------------------------------------------------------- |
| `--cases <file>`     | `cases.json`  | Список для прогону                                                                      |
| `--only <substr>`    | всі кейси     | Запускати лише кейси, чий ідентифікатор містить текст                                   |
| `--force`            | вимкнено      | Запустити кейс знову, навіть якщо `work/<id>/result.json` існує                         |
| `--keep`             | вимкнено      | Зберегти інсталяцію кейса, який пройшов. Кейс, який не пройшов, зберігається завжди     |
| `--no-pool`          | пул увімкнено | Не підсівати кожен кейс зі спільного пулу завантажень                                   |
| `--budget <minutes>` | 30            | Як довго холодний запуск може чекати вікно. Теплий запуск отримує щонайбільше 10 хвилин |

Він також читає дві змінні середовища. `MATRIX_STAGE=xvfb` вибирає етап Xvfb, описаний нижче. `MATRIX_DISPLAY_BASE` (типово 90) є першим номером дисплея, який використовує етап Xvfb. На десктопі ігри чутно; задайте `ALSOFT_DRIVERS=null`, щоб дати OpenAL бекенд, який нічого не грає.

Кейс, який уже має `result.json`, пропускається, тож прогін можна продовжити. Прогін завершується з кодом 1, якщо впав хоч один кейс.

### Що робить запуск {#what-a-launch-does}

Кейс збирає `case.opys` командою `opys build`, з однієї спільної конфігурації `matrix.config.mjs`, яка бере завантажувач, версію і Java зі змінних середовища. Провал збирання провалює кейс, і нічого не запускається. Інакше ранер запускає бандл з фіксованими змінними (`username=Player`, фіксований UUID, `token=0`) і `root` всередині каталогу кейса, спочатку холодно, а потім тепло. Теплий запуск іде лише якщо холодний пройшов.

Кожен запуск оцінюється у три кроки:

1. Ранер опитує вікно гри, доки бюджет не вичерпається або доки процес запуску не завершиться.
2. Коли вікно з’являється, він чекає до 90 секунд на рядок у лозі, який показує, що гра запустила звуковий рушій, побудувала атлас текстур або завантажила Forge, і ще 12 секунд після цього рядка. Якщо рядок так і не з’являється, він перевіряє після цих 90 секунд.
3. Він робить скриншот, якщо вікно досі на місці. Запуск зараховується, коли вікно досі існує, процес досі живий, а у лозі немає фатального рядка. Фатальні шаблони включають `Exception in thread "main"`, `Game crashed` і `Could not find or load main class`.

Отже, проходженням є вікно і живий процес, і далі воно не йде. Екран помилки завантажувача його задовольняє, тому скриншот варто відкрити. Ранер не надсилає грі жодного введення, тож гру судять за тим, що вона показує сама, на практиці за титульним екраном.

Результат кожного кейса потрапляє у `work/<id>/result.json`, а весь прогін у `work/summary.json`. Каталог також тримає `case.opys`, `build.log`, `cold.log`, `warm.log`, а також `cold.png` і `warm.png`, коли було видно вікно.

### Пул {#the-pool}

Перед встановленням кейса ранер жорсткими посиланнями підтягує у нього кожне завантаження, яке вже забрав попередній кейс, з `scripts/launch-matrix/pool`. У пул потрапляють лише файли, які маніфест називає фіксованим завантаженням. Файли, які створюють процесори завантажувача, у пул ніколи не потрапляють, а інсталятор далі сканує і перевіряє кожен. `--no-pool` вимикає це, і така прогонка чесніша, коли мережа дозволяє. Workflow передає `--no-pool`.

### Два етапи {#the-two-stages}

**Hyprland (типово).** На десктопі з Hyprland ранер створює безголовий монітор з іменем `opys-headless`, якщо його немає, кладе на нього робочу область і додає правила вікон, які відправляють туди вікна ігор. Ігри рендеряться на справжній відеокарті і ніколи не з’являються на екрані, яким ви користуєтеся. Скриншоти робляться засобом `grim`. Приберіть монітор після цього командою `hyprctl output remove opys-headless`.

**Xvfb (`MATRIX_STAGE=xvfb`).** Для машини без десктопа. Кожен запуск отримує власний дисплей Xvfb, з номерами від `MATRIX_DISPLAY_BASE`, 1280x720 з GLX і RANDR. Запуск іде з `LIBGL_ALWAYS_SOFTWARE=1` для програмного GL і `SDL_VIDEO_FORCE_EGL=1`, бо 26.3 відкриває вікно через SDL, якому на цьому дисплеї потрібен EGL. Вікно зараховується, коли воно має принаймні 300x200 і доступне для перегляду. Скриншоти робляться командою `import` з ImageMagick.

`scripts/launch-matrix/Dockerfile` є образом з усім, що потрібно етапу Xvfb. Зберіть його, змонтуйте репозиторій у `/work`, а всередині контейнера виконайте `mkdir -p ~/.local/share && npm ci && npm run build` (lwjgl3ify не стартує без цього каталогу), потім `MATRIX_STAGE=xvfb node run.mjs` у `scripts/launch-matrix`. Кілька ранерів можуть спільно використовувати один каталог `work/`, якщо їхні списки не перетинаються; дайте кожному власний `MATRIX_DISPLAY_BASE`.

### Workflow {#the-workflow}

`.github/workflows/launch-matrix.yml` виконується лише за `workflow_dispatch`. Він має два входи:

| Вхід    | Типово   | Дія                                                                                 |
| ------- | -------- | ----------------------------------------------------------------------------------- |
| `cases` | `slice`  | Який список запускати: `slice`, `key` (`cases.json`) або `full` (`cases.full.json`) |
| `only`  | порожньо | Запускати лише кейси, чий ідентифікатор містить цей текст                           |

Джоба працює на `ubuntu-latest` з етапом Xvfb. Вона перегенеровує списки, потім запускає `node run.mjs --cases <list> --no-pool --budget 10`, з `--only`, коли задано `only`. Її бюджет становить 10 хвилин, а не 30, як типово локально. Вона завантажує логи, скриншоти, результати кейсів і `summary.json` як артефакт, який зберігається 14 днів. Джоба має таймаут 300 хвилин і групу паралельності `launch-matrix`, яка не скасовує запущений прогін.

## Що CI виконує після пушу {#what-ci-runs-on-a-push}

`.github/workflows/ci.yml` виконується після пушу в `main` і після pull request у `main`. Він має чотири джоби.

| Джоба                       | Виконує                                                                                                                                                               |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Architecture boundaries     | `npm run test:architecture`, `npm run architecture`, `node scripts/release/crates.mjs` (перевіряє, що крейти публікуються у розв’язному порядку)                      |
| Cargo build + test          | `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo build --workspace --locked`, `cargo test --workspace --locked` |
| Cargo test (Windows)        | `cargo test -p opys-runtime --locked`                                                                                                                                 |
| TS build + typecheck + test | Після джоби Cargo: збирає `@opys/core-binding` і `@opys/runtime-binding`, потім `npm run build` для всіх робочих областей, `npm run typecheck`, `npm test`            |

Джоба Windows запускає лише тести крейта рантайму: його код прибирання і розпакування розгалужується на `\` проти `/` і згортає регістр на Windows, що тренує лише прохід справжньою файловою системою Windows.

## Чого не покрито {#what-is-not-covered}

- **Запуски на Windows і macOS.** Ніщо не стартує гру на Windows або macOS. Джоба Windows запускає тести одного крейту Rust, а тестової джоби macOS немає.
- **Усе після вікна.** Матриця доводить, що гра відкриває вікно і лишається запущеною. Вона не грає, не заходить на сервер і не перевіряє те, що гра показує, крім її лога.

## horno {#horno}

horno, jar Java, який запускає інсталятор завантажувача, є окремим репозиторієм (`../horno` від цього), і його тести є його власними.

```sh
./gradlew build                         # у репозиторії horno
jdk-probe/run.sh build/libs/<horno jar> # затінений jar, а не той з -sources
```

`./gradlew build` запускає набори JUnit 5 під `src/test/java`, які покривають код версій і завантажень, а також кроки патча, встановлення і профілю. Його джоба CI (`build.yml` у horno) збирає з Java 8.0.312 і завантажує затінений jar.

`jdk-probe/run.sh` ставить JDK на `PATH` (або `$JAVA_HOME`) запитання, на які спирається `ModuleUtil` у horno, описані у розділі про нутрощі JDK у [horno](/uk/internals/horno), і завершується ненульовим кодом на першій неправильній відповіді. Це єдина річ, яка повідомляє про JDK, де їх пересунули. CI horno запускає його на Java 17, 21, 25 і 27 як джобу `jdk-internals`.

Щоб спробувати локально зібраний horno на справжній інсталяції, прогоніть кейс з `--keep`, а потім підставте jar. Обидва виконуйте у `scripts/launch-matrix`:

```sh
node run.mjs --only forge-1.16.5 --keep
node probe.mjs forge-1.16.5-j8 <path to the built horno jar>
```
